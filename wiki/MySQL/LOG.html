MySQL Server 8.4 LTS · Log System

MySQL 日志系统：redo · undo · binlog

MySQL 的持久性、原子性与复制，全部由日志承担：redo log 让已提交的数据崩溃不丢，undo log 让未提交的数据能回滚并支撑 MVCC，binlog 记录逻辑变更供复制与恢复。本页从三套日志的写入路径、格式与崩溃恢复展开，并把每个知识点对应到 8.4 源码的文件与符号。

redo log
物理级重做日志（InnoDB）。WAL 先落盘，保证已提交事务不丢；循环复用，靠 checkpoint 推进。
undo log
逻辑回滚日志（InnoDB）。存"旧值"，支持回滚与 MVCC 版本链；由 purge 线程回收。
binlog
逻辑变更日志（Server 层）。记录语句或行变更，驱动主从复制与时间点恢复（PITR）。
01

日志家族：三套日志各司其职

Log Family

一句话区分：redo 管"已提交不丢"、undo 管"未提交能回滚 + 读旧版本"、binlog 管"变更被记录与复制"。redo/undo 属于 InnoDB 引擎层，binlog 属于 Server 层——这也是两阶段提交存在的根本原因（06 章 / 事务专题详述）。

维度redo logundo logbinlog
归属InnoDB 引擎层InnoDB 引擎层MySQL Server（SQL 层）
记录内容物理页级修改：page no + 偏移 + 新值（"这页这个位置改成什么"）逻辑旧值：行被改之前的样子（insert/update/delete 各自的逆向操作）逻辑变更：statement 或 row 格式的 SQL 事件
写入时机事务执行中，每个 mini-transaction（mtr）提交时持续写修改任何一行之前先写事务提交时一次性写出（组提交合并）
核心用途崩溃恢复：重放已提交修改（持久性 D）回滚 + MVCC 版本链（原子性 A + 隔离性 I）主从复制、PITR 恢复、审计
空间管理循环复用，checkpoint 推进后可覆盖undo 表空间，purge 线程回收已无引用记录追加式文件序列，过期/手动清理
8.4 源码入口storage/innobase/log/（log0sys.cc · log0write.cc · log0recv.cc）storage/innobase/trx/（trx0undo.cc · trx0rseg.cc · trx0purge.cc）sql/binlog.cc · sql/log.cc
关键理解：redo 与 undo 是"一对互逆的物理/逻辑日志"——redo 记录怎么改（向前重放），undo 记录改之前是什么（向后回退）。两者都写 ib_logfile* / redo 文件与 undo 表空间；而 binlog 由 SQL 层写出，与引擎日志不在一起，靠 XID 在两阶段提交中对账（05 章）。
02

redo log：WAL、LSN 与写入路径

Redo Log

redo 解决"崩溃前已提交的数据不丢"。原理一句话：先写日志、再改数据页（WAL）——因为日志是顺序追加写，数据页是随机写，日志先落盘的成本远低于数据页落盘，却能在崩溃后完整重放。

写入路径：从 mtr 到磁盘

InnoDB 里任何页修改都包在一个 mini-transaction（mtr） 里：mtr 提交时把改动追加到 redo log buffer，之后由日志线程批量刷盘。数据页则留在 buffer pool 中，等 checkpoint 或空闲时才落盘——"日志快、数据慢"。

redo 写入链：mtr → log buffer → fsync → 数据页。源码：storage/innobase/mtr/mtr0mtr.cc 的 mtr_commit()；日志对象 log_sys 在 storage/innobase/log/log0sys.cc，刷盘入口 log_write_up_to() 在 storage/innobase/log/log0write.cc。

LSN：日志的全局时钟

LSN（Log Sequence Number） 单调递增，同时标记"日志写到了哪"（log_sys->lsn）、"数据页刷到了哪"（flushed_to_disk_lsn）与"checkpoint 推进到哪"（checkpoint_lsn）。三者关系决定崩溃恢复的起点：只有 LSN > checkpoint_lsn 的 redo 需要重放。

LSN 三态区间。checkpoint 推进由后台线程周期性执行（log_checkpoint()，storage/innobase/log/log0chkp.cc），触发条件包括 redo 容量使用率、时间与脏页比例。

8.0.30 之后的 redo 重构

8.0.30 起 redo 模块从单文件 log0log.cc 拆分为一组职责单一的文件，并用 innodb_redo_log_capacity（默认 100MB，8.4 支持动态调整）取代旧的 innodb_log_file_size 固定文件组：日志文件不再需要手动规划大小，容量达到上限时自动触发 checkpoint 复用。

03

undo log：回滚与版本链

Undo Log

undo 是"改之前的旧值"。它有两个读者：事务回滚时沿链还原，MVCC快照读时沿链找可见版本——所以 undo 不是用完即删，要等"所有可能引用它的快照都消失"（purge）。

undo 记录类型

类型含义purge 时机源码常量
INSERT undo记录新插入行的主键——回滚时"删掉它"；因为插入行对其他事务不可见，提交后即可清理事务提交后即可 purge（无 MVCC 引用）TRX_UNDO_INSERT_REC
UPDATE undo记录被改行的旧版本（含旧值/旧隐藏列）——回滚时"改回去"；旧版本可能被其他事务的快照读到，必须保留直到所有 Read View 都不再引用（purge 判定）TRX_UNDO_UPD_EXIST_REC
DELETE 标记DELETE 在 InnoDB 里也是"更新"：先标记删除位（delete-mark），purge 阶段才真正物理移除MVCC 引用消失后物理清理TRX_UNDO_DEL_MARK_REC

版本链：roll_ptr 串起的历史

每行有隐藏列 roll_ptr，指向本行最近一次修改的 undo 记录；undo 记录里又存着"前一版本"的引用，于是形成 版本链。快照读沿链向前找第一个"对当前 Read View 可见"的版本——这正是 MVCC 的数据基础。

版本链 = 行（roll_ptr）+ undo 记录（前版本指针）。MVCC 可见性判定在 storage/innobase/read/read0read.cc 的 ReadView::changes_visible()，沿链构建旧版本在 storage/innobase/row/row0vers.cc 的 row_vers_build_for_consistent_read()（详见 MVCC 专题）。

回滚段与 purge

undo 记录按 回滚段（rollback segment） 组织，存放在独立的 undo 表空间（8.0 起默认 2 个，innodb_undo_tablespaces）。后台 purge 线程（innodb_purge_threads，默认 4）周期扫描：凡是"事务已提交且没有活动 Read View 引用"的 undo 记录，逐个物理清理。若长事务长期不提交，undo 无法回收，回滚段持续膨胀——这是"undo 暴涨"的根因。

运维要点：一个"开了 8 小时不提交"的事务会让整个 undo 表空间膨胀到数 GB，并连带放大 redo 与 MVCC 成本。排查入口：information_schema.innodb_trx 找长事务，配合 SHOW ENGINE INNODB STATUS 的 TRANSACTIONS 段看历史列表长度。
04

binlog：逻辑变更与复制

Binary Log

binlog 由 Server 层产生，记录"发生了什么变更"，是主从复制与 PITR（时间点恢复）的输入。它与 redo 的关键差异：redo 是引擎内部物理日志，binlog 是跨引擎的逻辑日志——这也决定了它们必须用两阶段提交对齐（05 章）。

三种格式

格式记录内容优缺点适用
STATEMENT原始 SQL 语句体积小；但依赖非确定性函数、锁等环境，主从不一致风险高8.0 默认已改 ROW
ROW每行变更的前/后镜像（binlog_row_image）确定性最好、复制最安全；体积大8.0 默认，推荐生产使用
MIXED自动选：安全语句用 STATEMENT，否则行记录两者折中；行为依赖引擎判定兼容性场景

binlog 文件里的"事件流"

binlog 是一个事件序列：文件以 FORMAT_DESCRIPTION_EVENT 开头，每个事务由 GTID/匿名 GTID、QUERY_EVENT（BEGIN）开始，行变更由 TABLE_MAP_EVENT + WRITE/UPDATE/DELETE_ROWS_EVENT 描述，最后以 XID_EVENT（含两阶段提交的 XID）收尾。

sql/rpl_utility.h 的 Log_event 家族；写入器 MYSQL_BIN_LOG（sql/binlog.cc）
binlog 事件流。8.4 中事件类继承自 Log_event（sql/rpl_utility.h），核心写入在 sql/binlog.cc 的 MYSQL_BIN_LOG::write_transaction()。

组提交：三阶段合并 fsync

高并发下每次提交都 fsync 是性能瓶颈。组提交把同一时刻到达的多个事务合并成一批：一次刷盘、一次落盘，多个事务共享一次 fsync 代价。8.0 的组提交分 flush / sync / commit 三个阶段，每阶段一个队列、一批处理。

binlog_group_commit_sync_delay（延迟收集批次，默认 0）· binlog_group_commit_sync_no_delay_count（凑够条数再刷）
组提交三阶段：flush → sync → commit。源码：sql/binlog.cc 的 MYSQL_BIN_LOG::commit() 与 process_commit_stage_queue()；引擎侧 innobase_commit()（storage/innobase/handler/ha_innodb.cc）。
GTID：8.0 复制默认 gtid_mode=ON。GTID（全局事务标识）让每个事务在全局唯一可溯源，复制断点续传时不再依赖"文件名+偏移"，而是"我执行到哪个 GTID 了"。源码见 sql/rpl_gtid.cc 的 Gtid_state。
05

崩溃恢复：redo 重放 + undo 回滚 + XID 对账

Crash Recovery

崩溃时内存里的数据页与日志进度不一致，恢复的目标是：已提交的补全（前滚）、未提交的还原（回滚）。完整流程是"redo 重放 → XID 对账 → undo 回滚"三步，8.4 由 storage/innobase/log/log0recv.cc 主导。

恢复流程

恢复主流程。源码：recv_recovery_from_checkpoint_start() / recv_recovery_rollback_active()（storage/innobase/log/log0recv.cc）；binlog 侧对账 MYSQL_BIN_LOG::recover()（sql/binlog.cc）。

innodb_force_recovery：出问题时的逃生梯

当 redo 损坏导致无法正常启动时，可用 innodb_force_recovery 逐级跳过检查进入只读模式，先抢救数据再重建。级别越高，跳过的功能越多、越不安全：

级别含义风险
1跳过崩溃恢复（不重放 redo）可能丢失已提交数据
2跳过回滚（不执行 undo 回滚）数据不一致，禁止写入
3跳过 undo 的 purge 与部分回滚只读，undo 可能残留
4跳过数据字典的加载检查只读，表空间状态不可靠
5跳过 undo 表空间读取只读，MVCC 回退不可用
6跳过 redo 读取，不加载日志文件只读，仅用于"导出数据"
红线：force_recovery 是"导出数据"手段，不是长期运行配置——一旦数据导出完毕，应重建实例（mysqldump / 物理备份恢复），严禁在 force_recovery 下持续提供服务。

日志参数与实践

Parameters & Ops

日志相关参数横跨引擎与 Server 两层，配置的核心矛盾是安全性与性能：刷盘越勤越安全、也越慢。下面是 8.4 常用参数速查。

高频问题与排查

  • redo 写满 / 日志刷盘慢：检查 SHOW ENGINE INNODB STATUS 的 LOG 段（lsn 与 checkpoint 差值、日志写入速率），调大 innodb_redo_log_capacity 或优化长事务
  • undo 膨胀：用 information_schema.innodb_trx 找出超长事务，业务层限制事务时长；确认 purge 线程正常（innodb_purge_threads）
  • binlog 暴涨：ROW 格式下大事务产生海量行镜像——控制单事务行数，配合 binlog_row_image=MINIMAL（只记变更列）
  • 查看日志：SHOW BINARY LOGS（文件列表）、SHOW BINLOG EVENTS（事件流）、mysqlbinlog（离线解析）
双写缓冲（doublewrite）：与 redo 互补的 InnoDB 数据页保护——redo 记录页内改动，但"半页写"（页写一半断电）会同时损坏旧数据与新日志，双写先落一份完整页副本再改页，避免此坑。参数 innodb_doublewrite（8.0 起默认 ON）。
