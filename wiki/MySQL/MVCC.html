MYSQL INNODB · MULTI-VERSION CONCURRENCY CONTROL · 8.4

MVCC：用「版本」换「并发」
可见性判定 —— 隔离性的理论核心

MVCC（多版本并发控制）是 InnoDB 实现隔离级别的基石：快照读不加锁、不互等，而是为每次读建立一份一致性视图（ReadView），沿记录的版本链挑出"对自己可见"的那个版本。理解 MVCC，就是理解组件怎么协作、可见性怎么判定这两件事。

01 · SNAPSHOT READ
快照读不加锁
普通 SELECT 走一致性读，不申请行锁，与写并发互不阻塞。
02 · VERSION CHAIN
一行多个版本
每次更新不覆盖旧值，旧版本写入 undo log，由 DB_ROLL_PTR 串成链。
03 · READ VIEW
一致性视图判定
ReadView 的四要素（上/下水位、活跃列表、创建者）决定每个版本可见与否。
01

先直观理解：一条记录的"时光轴"

INTUITION

MVCC 的核心思想一句话：读请求不等待写请求。写的人只管往"时间轴"上追加新版本，读的人拿一份"快照清单"，沿时间轴找到对自己可见的那个版本。双方各读各的，永不互相阻塞。

图 1 · 版本链（时间轴视角）：每次更新把旧版本压入 undo log，新版本通过 DB_ROLL_PTR 指回旧版本；读请求按自己的 ReadView 决定停在链上哪个版本。
两个前提概念 —— 快照读（一致性读）：普通 SELECT，不加锁，靠 ReadView + 版本链构造可见结果；当前读（锁定读）：SELECT ... FOR UPDATE / LOCK IN SHARE MODE、UPDATE、DELETE，读最新版本并加锁。MVCC 只管前者，后者交给锁系统（next-key lock 等）。
02

三大组件如何协作

COMPONENTS & COLLABORATION

MVCC 不是单个机制，而是 隐藏列 + undo 版本链 + ReadView 三个组件的协同：写路径负责造版本，读路径负责选版本，purge 线程负责清旧版本。

A · DATA RECORD

聚簇索引记录 + 隐藏列

InnoDB 聚簇索引的每行记录，除用户列外还携带两个系统隐藏列：DB_TRX_ID（本版本由哪个事务写入）与 DB_ROLL_PTR（指向 undo log 中的旧版本）。版本号就是事务 id，全局单调递增。

row { id=7, name='alice'
  DB_TRX_ID=18, DB_ROLL_PTR→undo#8 }
B · UNDO LOG

undo 版本链

旧版本的数据不在数据页里，而存在 undo log 中（逻辑逆操作 + 旧值）。insert undo 只用于回滚（行删除后即断链），update undo 承载版本链，链头被 DB_ROLL_PTR 引用。

TRX_UNDO_INSERT_REC = 11
TRX_UNDO_UPD_EXIST_REC = 12
TRX_UNDO_UPD_DEL_REC = 13
C · READ VIEW

一致性视图（ReadView）

创建快照那一刻，把全局活跃事务快照下来：上水位、下水位、活跃列表、创建者。它是判定"某版本可见与否"的唯一裁判。

m_up_limit_id  = 10
m_low_limit_id = 30
m_ids         = [12,17,20]
m_creator_trx_id = 15

读路径：沿版本链"挑版本"

定位记录取出聚簇索引当前版本，读 DB_TRX_ID
→
判定可见性ReadView.changes_visible(trx_id)
→
可见？是 → 直接返回该版本
→
不可见？沿 DB_ROLL_PTR 取上一版本，回到第 2 步
→
链走完仍不可见行对当前事务不可见（跳过）

在源码中，这个"沿链找可见版本"的过程由 row/row0sel.cc 的 row_sel_build_prev_vers_for_mysql() 完成：每拿到一个旧版本，先经 changes_visible() 判定，不满足就继续向链头回溯；row_vers_old_has_index_entry()（row/row0vers.cc）则负责判断旧版本在二级索引中是否有对应入口（用于覆盖索引/ICP 场景）。

写路径：只追加，不覆盖

拷贝旧值把当前版本写到 undo log，生成 undo 记录
→
更新隐藏列DB_TRX_ID = 本事务 id
→
挂接链条DB_ROLL_PTR 指向刚写的 undo 旧版本
→
等 purge旧版本保留，直到所有视图不再需要它
purge 的"水位" —— trx/trx0purge.cc 的清理线程以全局最老的活跃 ReadView 为水位：水位之下的旧版本已不可能被任何活跃视图读到，可以物理删除。这就是"长事务拖垮 undo"的根源：视图老，purge 不敢动手。
03

可见性判定：两个水位 + 一次二分

CHANGES_VISIBLE ALGORITHM

判定一个版本是否可见，本质是把它的写入事务 id 放进 ReadView 的坐标系里对号入座。坐标系由两个水位划出三个区，再加上活跃列表的二分查找，O(log n) 内完成。

可见区：事务已提交，必见 活跃区：需要查活跃列表 m_ids 不可见区：未来事务，必不见 m_ids 中的活跃事务（打点）

读法：m_up_limit_id 是创建视图时活跃事务集合中最小的 id —— 比它还小的 id 必然已提交，直接可见；m_low_limit_id 是下一个待分配的事务号 —— 达到它的 id 必然还没开始，直接不可见；两个水位之间的 id 是否可见，取决于它是否还在活跃列表 m_ids 里。

判定四步（与源码逐行对应）

STEP 1 · 快路径
已提交 或 自己
id < m_up_limit_id
|| id == m_creator_trx_id

比上水位小的必已提交；创建者自己的写入必然可见。

→ 可见
STEP 2 · 未来事务
下水位之外
id ≥ m_low_limit_id

达到下水位的 id 在视图创建时尚未分配，属于"未来事务"。

→ 不可见
STEP 3 · 无活跃
活跃列表为空
m_ids.empty()

灰色地带没有活跃事务，则中间 id 全部已提交。

→ 可见
STEP 4 · 二分查找
是否在活跃列表中
binary_search(m_ids, id)

m_ids 有序，二分 O(log n)。不在列表中 = 已提交。

→ 可见（在列表中则不可见）

源码直读：read0types.h 的 changes_visible()

// storage/innobase/include/read0types.h:163
bool changes_visible(trx_id_t id, const table_name_t &name) const {
  ut_ad(id > 0);
  // STEP 1：上水位以下（必已提交）或创建者自己 → 可见
  if (id < m_up_limit_id || id == m_creator_trx_id) {
    return (true);
  }
  check_trx_id_sanity(id, name);
  // STEP 2：达到下水位（未来事务）→ 不可见
  if (id >= m_low_limit_id) {
    return (false);
  } else if (m_ids.empty()) {
    // STEP 3：灰色地带无活跃事务 → 可见
    return (true);
  }
  // STEP 4：有序数组二分查找，不在活跃列表 → 已提交，可见
  const ids_t::value_type *p = m_ids.data();
  return (!std::binary_search(p, p + m_ids.size(), id));
}
容易踩的坑 —— 三个边界语义：① m_up_limit_id 取的是活跃事务中最小的 id，不是"当前最大已提交 id"；② m_low_limit_id 是下一个待分配号，所以用 >= 判不可见；③ 灰色地带里已提交的事务（如 id=25）虽然"时间上晚于视图创建"，但它提交了就不在 m_ids 里 —— 这正是 RC 下"每次语句都能看到最新已提交"的机制来源。

05

快照的诞生与生命周期

SNAPSHOT LIFECYCLE

ReadView 不是一直存在，而是在第一条一致性读语句执行时由 trx_assign_read_view()（trx/trx0trx.cc:2319）创建，并随隔离级别决定活多久。这正是 RC 与 RR 行为差异的全部秘密。

T0 · BEGIN

事务开始，还没有任何视图

写事务才分配 trx_id；纯快照读事务在创建视图时才取号。

T1 · 第一条 SELECT

trx_assign_read_view() 创建 ReadView

快照当前全局活跃事务（trx_sys 的读写事务链表），算出上/下水位与活跃列表，存入 trx->read_view。

T1 → Tn · RR

REPEATABLE READ：视图保持到事务结束

之后所有一致性读复用同一视图，所以同一事务内多次读到同一快照 —— 可重复读成立。

每条语句 · RC

READ COMMITTED：每条语句重建视图

语句结束时视图即释放，下一条语句创建新视图 —— 每次都能看到"最新已提交"，出现不可重复读。

Tn · COMMIT / ROLLBACK

视图随事务释放

视图销毁后，被它"护住"的旧版本失去保护，purge 水位前进，逐步物理清理。

快照读 vs 当前读：MVCC 与锁的分工

快照读（一致性读）

SELECT（不带 FOR UPDATE / LOCK IN SHARE MODE），也包含部分 DML 的"读旧值"环节。

  • 不加锁，不参与锁等待，读永不阻塞写
  • 走 ReadView + 版本链，由 changes_visible 选版本
  • RU 直接读最新版本（无视图）；RC 语句级视图；RR 事务级视图

当前读（锁定读）

SELECT ... FOR UPDATE / LOCK IN SHARE MODE、UPDATE、DELETE、INSERT。

  • 必须加锁（LOCK_S / LOCK_X、next-key lock），读最新已提交版本
  • MVCC 不参与，走 lock/lock0lock.* 的锁系统
  • RR 下靠 next-key lock（临键锁） 防止当前读的幻读
面试常考点 —— "MVCC 解决了幻读吗？"准确回答：快照读场景下 RR 靠固定视图天然无幻读；当前读场景下靠 next-key lock。二者合起来，才是 MySQL 的 RR 隔离级别的完整语义。

四个隔离级别在源码中的落点

ISOLATION LEVELS

隔离级别枚举定义在 SQL 层 sql/handler.h:3186：ISO_READ_UNCOMMITTED / ISO_READ_COMMITTED / ISO_REPEATABLE_READ / ISO_SERIALIZABLE。级别越高，MVCC 让位越多、锁介入越多。

隔离级别快照策略读行为副作用关键机制
READ UNCOMMITTED不建视图直接读最新版本（含未提交）脏读MVCC 失效，退化为裸读；InnoDB 下实际仍读已提交居多，但语义上是脏读
READ COMMITTED语句级视图每条语句看到最新已提交不可重复读、幻读语句结束视图即失效；判定灰色地带"不在活跃列表即可见"的典型体现
REPEATABLE READ
InnoDB 默认		事务级视图整个事务看到同一快照快照读无幻读；当前读靠 next-key lock视图保持到事务结束；purge 水位被它牵制
SERIALIZABLE快照读退化为当前读所有读都加锁（含 SELECT）并发度最低MVCC 基本让位于锁：一致性读也变成锁定读，靠锁保证串行
记忆锚点 —— 两条轴：视图寿命（无视图 → 语句级 → 事务级 → 锁替代）与锁介入程度（无锁 → 少量 → 快照读无锁 + 当前读临键锁 → 全加锁）。RC 与 RR 的差别只在视图寿命，判定算法一字未改 —— 这是 MVCC 设计最精妙的地方。

08

面试高频题速答

INTERVIEW Q&A
Q1 · MVCC 到底解决了什么问题？
读写不互斥：读（快照读）不加锁、不等待，通过多版本让"读旧版本"与"写新版本"并发进行。它解决的是读-写并发，写-写冲突仍然靠锁。
Q2 · RR 为什么能防幻读？快照读和当前读答案不同
快照读：视图固定在整个事务内，新增行即使提交也不在当前视图可见，天然无幻读；当前读：SELECT ... FOR UPDATE 等走 next-key lock，锁住记录及其间隙，阻止新行插入。两者合起来构成 MySQL 的 RR 语义。
Q3 · 可见性判定为什么用二分查找？
活跃事务列表 m_ids 在创建视图时按 id 升序快照，之后只读不写；对有序静态数组用 std::binary_search 是 O(log n)，且无锁无同步成本。这是读热路径，性能设计极苛刻。
Q4 · undo 为什么分 insert 和 update 两类？
insert undo 只在回滚时用（删除自己插入的行），行删除后链条即断，无需被版本链引用；update undo 要承载版本链（供快照读回溯旧版本），生命周期受 purge 水位控制。分开管理是为了让 insert undo 可以更早被清理。
Q5 · 为什么长事务会拖垮数据库？
长事务持有的 ReadView 成为全局最老视图，purge 水位无法前进，被它护住的旧版本（undo）不能物理删除 —— undo 膨胀、表空间增长，二级索引回表也要遍历更长的版本链。优化手段：缩短事务、拆分大事务、监控长事务。
