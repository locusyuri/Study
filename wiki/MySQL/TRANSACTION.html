MySQL Server 8.4 LTS · Transaction & Concurrency

MySQL 事务与并发：ACID、锁与隔离级别

事务是"一批要么全成、要么全废的操作"，并发是"多个事务同时跑还能不错"。MySQL 用两套机制回答这两个问题：锁（悲观地挡掉写写冲突）与 MVCC（乐观地让读写互不阻塞），底层由 redo / undo 日志支撑 ACID。本页从三套机制展开，并把每个知识点对应到 8.4 源码的具体文件与符号。

机制 1 · 锁
写-写冲突的裁判
行锁 / 间隙锁 / 临键锁，S 与 X 兼容矩阵
机制 2 · MVCC
读-写不互斥
快照读走 Read View，当前读才加锁（详见 MVCC 专题）
机制 3 · 日志
redo / undo
WAL 保证持久性，undo 保证原子性与回滚
01

事务的本质：ACID 与状态机

Transactions

一句话版本：事务把多条 SQL 打包成"要么全部生效、要么全部撤销"的原子单元。ACID 四性不是四个并列特性，而是由日志与锁分层保障的——理清"哪个机制负责哪条承诺"是理解事务源码的第一步。

ACID 四性与保障机制

A

原子性 Atomicity

部分成功 = 全部失败。靠 undo log：事务崩溃或 ROLLBACK 时，用 undo 把已改的行逐条还原。

trx_rollback() / trx_undo
storage/innobase/trx/trx0roll.cc
C

一致性 Consistency

约束不破坏。靠应用层 + 引擎约束：外键、唯一键、CHECK 在写入时校验；引擎保证"崩溃前后约束一致"。

唯一性检查 row_ins_dupl_error_with_rec()
外键 dict_foreign_t / row0foreign.cc
I

隔离性 Isolation

并发事务互不干扰。靠锁 + MVCC：写-写互斥由锁保证，读-写不阻塞由 MVCC 快照保证。

锁：lock0lock.cc
MVCC：row_vers / read_view（详见 MVCC 专题）
D

持久性 Durability

提交即不丢。靠 redo log + WAL：提交前先写重做日志（顺序 IO），数据页延迟落盘，崩溃后按 LSN 重放。

log_write_up_to() / mtr 提交
storage/innobase/log/log0log.cc
记忆：A 靠 undo、D 靠 redo、I 靠锁+MVCC、C 是前三者共同的结果——事务系统在源码里就是三棵主干：锁（lock）、MVCC（read view + undo 版本链）、日志（redo + undo），其余都是这三者的衍生。

事务状态机

InnoDB 事务对象 trx_t（storage/innobase/include/trx0trx.h）用 trx_state_t 枚举维护生命周期：写事务先 ACTIVE，COMMIT 时先进入 PREPARED（两阶段提交，见 06 章）再 COMMITTED；失败则回滚到 NOT_STARTED。只读事务不分配 trx_id，这是 8.0 的优化。

InnoDB 事务状态（trx_state_t，storage/innobase/include/trx0trx.h）：ACTIVE → PREPARED → COMMITTED 是提交路径；ACTIVE → ABORTED 是回滚路径。源码函数：trx_start() / trx_commit() / trx_rollback()。SQL 层事务入口在 sql/transaction.cc（trans_commit() / trans_rollback()）。
02

InnoDB 锁体系：粒度、模式与兼容

Lock System

锁是"写-写冲突"的裁判。InnoDB 的锁分两个维度：粒度（表锁 / 行锁）与 模式（共享 S / 排他 X）。行锁是 InnoDB 的默认武器——它实际锁的不是"行记录"，而是索引记录（因此没有索引的 WHERE 会退化成全表加锁）。

锁的粒度与类型

锁类型作用对象语义与场景源码符号
表锁 · 意向锁
IS / IX		整张表行锁的"前置声明"：加行锁前先对表加意向锁，表级操作（DDL）据此判断"表上是否有行被占用"，避免逐行检查lock_table() · LOCK_IS / LOCK_IX
表锁 · 显式

S / X 兼容矩阵

兼容性决定"能不能共存"：X 与任何锁都冲突，S 只与 S 兼容。矩阵同时适用于表锁与行锁——这是 InnoDB 判断锁冲突的唯一规则（源码 lock_compatible()）。

关键理解：意向锁（IS/IX）本身不锁数据，它只告诉别人"我这表上有行级 S/X 锁"，让表级操作（如 DDL 的 LOCK_TABLES）能快速判断能否进行。行锁与意向锁在 storage/innobase/include/lock0priv.h 的 lock_t 中统一描述（type_mode 高 4 位是类型，低 4 位是模式）。

哪些语句会加什么锁

语句加锁说明
SELECT ... （普通）不加锁（快照读）走 MVCC Read View，不阻塞任何写；见 04 章
SELECT ... FOR SHARES 行锁（+间隙）当前读；其他事务可读不可写
SELECT ... FOR UPDATEX 行锁（+间隙）当前读；其他事务读可（快照）写不可
UPDATE / DELETEX 行锁（+间隙）先按 WHERE 定位（当前读）再加 X 锁，然后才修改
INSERTX 行锁 + 插入意向锁先插入意向锁探测间隙，冲突则等待；插入后对记录持 X 锁

加锁的底层入口是 storage/innobase/lock/lock0lock.cc：行锁 lock_rec_lock() 与表锁 lock_table()；等待挂起在 lock_wait_suspend_thread()（05 章详述）。SQL 层通过 sql/lock.cc（Lock_tables_precheck）与 MDL 管理表级元数据锁。

03

隔离级别与并发问题

Isolation Levels

隔离级别是"并发正确性"与"并发性能"之间的刻度。MySQL 默认 REPEATABLE READ（与 ANSI 标准默认不同，因为 InnoDB 的 RR 通过 MVCC + 间隙锁实际上消除了幻读）。理解隔离级别，先看它要防住的四种并发问题。

四种并发问题

问题发生条件举例（余额账户）被谁防住
脏读
Dirty Read		读到未提交事务的修改A 转出 100 未提交，B 读到余额少了 100RC 及以上（MVCC 只看已提交版本）
不可重复读
Non-Repeatable		同一事务两次读，值被其他已提交事务改掉T1 两次查余额，中间 T2 提交了扣款RR（MVCC 固定快照）
幻读
Phantom		同一事务两次范围查询，行数变化（其他事务插入）T1 查"余额>0"得 3 行，T2 插入 1 行后 T1 再查得 4 行RR 的间隙锁 / 临键锁（当前读场景）
丢失更新
Lost Update		两个事务读-改-写同一行，后者覆盖前者T1、T2 都读到 100，各自 +50 后写回，最终 150 而非 200需应用层 FOR UPDATE 或乐观锁（引擎不自动防）

隔离级别 × 并发问题

隔离级别脏读不可重复读幻读实现要点（InnoDB）
READ UNCOMMITTED可能可能可能不加锁读，能看到未提交版本（几乎不用）
READ COMMITTED防住可能可能每条语句新建 Read View；无间隙锁
REPEATABLE READ（默认）防住防住防住（快照读）；当前读靠临键锁事务首次读时建 Read View；当前读加临键锁
SERIALIZABLE防住防住防住所有读都变当前读（自动加锁）
源码：隔离级别在 SQL 层由系统变量 transaction_isolation 承载（sql/sys_vars.cc 的 Transaction_isolation），InnoDB 侧存入 trx_t::isolation_level（storage/innobase/include/trx0trx.h）；判定"能否看到某版本"在 storage/innobase/read/read0read.cc 的 ReadView::changes_visible()（MVCC 专题已详述）。

RR 为什么能防幻读：临键锁的"左开右闭"

RR 级别下，当前读（FOR UPDATE / UPDATE / DELETE）加的是临键锁：锁住命中记录本身 + 记录前方间隙，把"记录之间的空位"也圈住。这样其他事务既改不了这些行，也插不进这些空位——第二次范围查询的行数就不会变。这也是 InnoDB 与标准 RR 的最大差异：MySQL 的 RR 实际达到了类似可串行化（当前读部分）的效果。

临键锁 = 记录锁 + 前间隙锁。MySQL 官方把 RR 的当前读描述为"锁覆盖到左开右闭区间"；storage/innobase/lock/lock0lock.cc 中 lock_rec_has_expl_gap() / LOCK_ORDINARY 实现该语义。
04

快照读与当前读：并发控制的分工

Snapshot vs Current Read

InnoDB 的并发控制不是"要么锁死、要么放任"，而是把读分成两种：快照读（不加锁，走 MVCC）和当前读（加锁，读最新已提交版本）。读-写不互斥正是靠"快照读"实现的——这是 InnoDB 高并发吞吐的根基。

维度快照读（一致性读）当前读（加锁读）
语句SELECT（普通）SELECT ... FOR SHARE / FOR UPDATE、UPDATE、DELETE、INSERT
读取内容Read View 可见的版本（可能不是最新，但"读的时候是稳定的"）最新已提交版本（必须是最新的，否则写错行）
加锁不加锁加 S/X 行锁（+间隙锁按隔离级别）
阻塞永不阻塞、永不被阻塞（无锁）与其他写锁互斥，可能锁等待
快照时机RR：事务内首次读建 Read View；RC：每条语句新建无快照，始终读最新
对应源码InnoDB 统一走 storage/innobase/row/row0sel.cc 的 row_search_mvcc()；是否加锁由 prebuilt->select_lock_type（LOCK_NONE / LOCK_S / LOCK_X）决定

典型场景推演：读-写并行

T1 开启事务做快照读（普通 SELECT），T2 同时更新并提交同一行——两者完全并行：T1 读自己的快照（旧值），T2 写新值。若 T1 之后做当前读（FOR UPDATE / UPDATE），才会看到最新值，并可能因 T2 仍持锁而等待。

同一行的读写并行：T1 的快照读不因 T2 的写锁而阻塞（MVCC 版本链 + Read View）；直到 T1 改为当前读才会与 T2 的 X 锁相遇。源码关键：row_search_mvcc() 中 sel_set_rec_lock() 决定是否加锁，ReadView 决定读哪个版本。
与 MVCC 专题的关系：本页 04 章讲"快照读与当前读的分工"，MVCC 专题则深入 Read View 的构造、changes_visible() 判定算法与版本链的组装——两者合起来才是 InnoDB 读路径的全貌。
05

锁等待与死锁

Lock Wait & Deadlock

锁冲突不可避免，冲突的结果只有两种：等待（对方很快释放）或死锁（双方互等、谁也无法继续）。InnoDB 用"等待超时 + 死锁检测"两套机制兜底。

锁等待：挂起线程与超时

加锁失败时，当前事务进入等待：InnoDB 把线程挂起在 lock_wait_suspend_thread()（storage/innobase/lock/lock0wait.cc），并周期性检查锁是否可得、是否超时。超时上限由 innodb_lock_wait_timeout（默认 50 秒）控制；超时后事务报错并回滚（仅回滚当前语句或整个事务，取决于 innodb_rollback_on_timeout）。

调优点：线上高并发场景 50 秒太长——等待链会堆积、连接被占满。常见做法是调到 2~5 秒，让等锁失败快速暴露，而不是拖垮整个连接池。

死锁：互等即环

死锁的本质是等待图（wait-for graph）中出现环。下面的经典场景：T1 持有行 A、想锁行 B；T2 持有行 B、想锁行 A——两个事务各持一锁、各等一锁，永远解不开。

死锁检测：InnoDB 周期性地构建等待图（storage/innobase/lock/lock0wait.cc 的 lock_deadlock_occurs()），发现环后选择回滚代价最小的事务（undo 行数最少者），回滚并返回 ER_LOCK_DEADLOCK（1213）错误；开关 innodb_deadlock_detect。

死锁示例与处置

-- 事务 1                            -- 事务 2
BEGIN;                               BEGIN;
UPDATE account SET b=b-10 WHERE id=1;      UPDATE account SET b=b-10 WHERE id=2;
UPDATE account SET b=b+10 WHERE id=2;      UPDATE account SET b=b+10 WHERE id=1;   ← 死锁
COMMIT;                              -- 其中一个收到: Deadlock found (1213)
  • 业务侧：应用必须捕获 1213 并重试整个事务——死锁是引擎的正常行为，不是 bug
  • 设计侧：让所有事务按同一顺序访问资源（如都先 id=1 再 id=2），破坏"环"
  • 诊断：SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段给出持锁/等待的完整回溯
06

redo / undo：ACID 的日志底座

Redo & Undo

锁和 MVCC 解决"并发时不错"，日志解决"崩溃时不丢、不半截"。redo log 保证持久性（已提交不丢），undo log 保证原子性（未提交能回滚），两者配合完成崩溃恢复。

redo log：WAL 与 LSN

① 修改内存页
数据页在 buffer pool 中修改，不立即落盘
→
② 写 redo 日志
把"页改动"追加到 redo log buffer（顺序 IO），记录 LSN
→
③ 提交确认
日志落盘（fsync）后，事务才算提交成功
→
④ 后台刷脏
脏页按 checkpoint 延迟落盘
→
⑤ 崩溃重放
启动时按 LSN 从 checkpoint 重放 redo

这就是 WAL（Write-Ahead Logging）：日志先落盘、数据后落盘，顺序写远快于随机写。LSN（Log Sequence Number） 单调递增，是 redo、数据页、checkpoint 对齐的"全局时钟"。8.0 引入 innodb_redo_log_capacity（默认 100MB）代替旧的固定日志文件组，支持动态扩容。

undo log：原子性与版本链

每次修改行前，InnoDB 先写一条 undo 记录（存旧值），并挂到该行的版本链上（行的隐藏列 roll_ptr 指向链头）。undo 有两个读者：回滚（事务失败时沿链还原旧值）和 MVCC（快照读沿链找可见版本）。已提交且无快照引用的 undo 记录，由后台 purge 线程回收。

源码联动：回滚走 storage/innobase/trx/trx0roll.cc 的 trx_rollback()；undo 记录类型在 storage/innobase/include/trx0rec.h（TRX_UNDO_INSERT_REC / TRX_UNDO_UPD_EXIST_REC）；MVCC 沿链查找见 storage/innobase/row/row0vers.cc 的 row_vers_build_for_consistent_read()。

两阶段提交：redo 与 binlog 的一致性

开启 binlog 后，一次提交涉及两套日志（引擎 redo 与 SQL 层 binlog），必须用两阶段提交保证崩溃时两者不矛盾（否则恢复后主从数据不一致）。8.0 中 binlog 写入演进为组提交（group commit）合并 fsync。

binlog 有 XID → 补提交；没有 → 回滚
两阶段提交：prepare → binlog → commit。源码：sql/binlog.cc 的 MYSQL_BIN_LOG::commit() 与 storage/innobase/handler/ha_innodb.cc 的 innobase_commit() / innobase_prepare()；恢复对账在 recover_from_binlog_xids()。
