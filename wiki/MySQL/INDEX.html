MySQL 索引：B+树、InnoDB 存储与查询优化

索引的本质，是用有序的数据结构换取磁盘 IO 的减少。理解 MySQL 的索引，就是理解三条主线：为什么是 B+树（数据结构）、聚簇与二级索引如何落盘（InnoDB 物理存储）、优化器如何利用索引（SQL 执行）。本页从这三条主线展开，并把每个知识点对应到 8.4 源码中的具体文件与符号。

01

索引的本质：用有序换少读

Why Index

一句话版本：索引像书的目录——先确定记录的大致位置，再精确定位，而不是逐页翻书。数据库的"翻书"成本不是 CPU，而是磁盘 IO：一次随机读一个 16KB 数据页，远比在内存里比较几千行贵。

直观理解

没有索引时，InnoDB 只能做全表扫描：把每一页读进内存，逐行比较 WHERE 条件。100 万行的表就要读约 1.5 万页（按每页 65 行估算），且行在页内无序，无法提前跳读。有了索引后，先沿 B+树从根走到叶，只读 3~4 页就定位到目标行所在的数据页，再读这一页即可——IO 从"万级"降到"个位数"。

关键视角：索引优化的核心指标只有一个——访问路径上要读多少个数据页。B+树把"找到目标行"从 O(n) 页扫描变成 O(log n) 次树下降，这就是全部收益的来源。

B+树容量：为什么 3 层就够

B+树每下降一层，可覆盖的记录数乘上"扇出"（每个内节点页能装的子节点指针数）。按 8 字节主键 + 6 字节页号的内节点记录估算，一个 16KB 页约可容纳 1000 个键；叶子页按每行约 150B 估算约 100 行/页：

树高 1 层（根 + 叶）约 100 行
树高 2 层约 10 万行
树高 3 层约 1 亿行
树高 4 层约 1000 亿行
示意图口径：扇出 1000（内节点每页约 1000 个键）、叶子页约 100 行/页；数值随主键宽度与行宽变化，仅用于说明"高度增长极其缓慢"。结论：百万行 ≈ 3 层，十亿行 ≈ 4 层——每多一层，一次查找只多 1 次磁盘 IO。

复杂度对比

访问方式IO 数量级说明适用

02

B+树：索引的物理形态

B+Tree

InnoDB 的索引全部是 B+树（聚簇索引也是）。B+树把"有序数组"和"树形跳读"结合：内节点只存键与指针（不存数据），因此扇出极高；叶子节点存全部数据且按序串联成链表，因此范围扫描天然连续。这是一套为磁盘量身定做的结构。

一次索引查找，3 次 IO

下面演示查找键值 42 的完整路径（MySQL 8.4 中对应 storage/innobase/btr/btr0cur.cc 的 btr_cur_search_to_nth_level()）：根页读入后二分比较 30 < 42 < 70，走中间指针；内节点页读入后 40 < 42 < 55，走对应指针；叶子页读入后页内二分定位到行。点击按钮逐步查看。

B+树查找键值 42：每层一次 IO，页内二分比较键区间。内节点不存数据、只存"键 + 子页指针"，是扇出高的根本原因；叶子页之间通过链表串联，支撑范围扫描。源码入口：btr_cur_search_to_nth_level()，游标类型 btr_cur_t（storage/innobase/include/btr0pcur.h）。

为什么偏偏是 B+树

结构有序遍历范围查询磁盘扇出写放大结论
哈希表否否—低等值 O(1) 极快，但无法排序/范围；InnoDB 仅以 AHI 形式做内存加速缓存
二叉搜索树是是2（每节点 2 指针）高（频繁旋转）百万行树高 ~20，每层一页 IO，磁盘上不可接受；仅内存场景可用
B 树是需要中序遍历高（数百~千）中数据分散在所有节点，范围扫描要跨层回溯，页利用率不稳定
B+树是是（叶子链表）高（数百~千）中（页分裂）InnoDB 的选择：内节点纯键指针、叶子串链，范围/排序/聚簇天然一体
一句话：B+树牺牲了内节点的"数据存储"，换来了更高的扇出（更矮的树）和叶子节点的顺序链表（高效范围扫描）——这两点恰好是磁盘数据库最贵的两件事：IO 次数和顺序性。

数据页内部：页目录与二分

B+树的最底层是数据页。一个 16KB 页内，记录按主键（或索引键）有序排列在 User Records 区；页尾的 Page Directory（页目录）为每 4~8 条记录建立槽，指向该组第一条记录的偏移。查找页内记录时先对槽做二分，再在槽内做线性扫描——这就是"页内查找"的源码实现（storage/innobase/include/page0page.h 的 page_cur_search_with_match()）。

页内区域源码符号作用
页头FIL_PAGE_DATA / page_header页类型、上一页/下一页指针、页内记录数等元信息
User RecordsPAGE_DATA实际记录，按键序排列，通过记录头的 next/prev 偏移形成单向链表
Page DirectoryPAGE_DIR_SLOT / PAGE_N_DIR_SLOTS槽数组，槽指向每组首记录；查找时对槽二分、槽内线性扫
页尾FIL_PAGE_END_LSN页级校验与恢复（checksum、LSN），崩溃恢复时校验页完整性
03

聚簇索引与二级索引：InnoDB 的存储骨架

Clustered & Secondary

InnoDB 的表本身就是一棵以主键为键的 B+树（聚簇索引），叶子节点存放完整行。其余每个索引都是独立的一棵 B+树（二级索引），叶子节点只存"索引键 + 主键"。两者通过主键桥接——这也是"回表"的由来。

两棵树，两种叶子

维度聚簇索引（主键树）二级索引（辅助树）
叶子内容完整行数据（含隐藏列：row_id、trx_id、roll_ptr）索引键列 + 主键列
每表数量至多 1 棵（主键 / 唯一键 / 隐式 row_id）可多棵，每棵独立 B+树
查找语义按主键直接拿整行，无需二次跳转命中后拿到主键，还需回聚簇树取行
数据组织行按主键物理有序，页内/页间有序行按索引键有序（键序，非物理序）
源码定义dict_index_t（storage/innobase/include/dict0dict.h）；flags 标记 DICT_CLUSTERED / DICT_UNIQUE 等

回表：一次额外的随机 IO

用二级索引 idx_name(name) 查 WHERE name='alice'：先在二级树里定位到 (alice, 主键=7)，再拿主键 7 回聚簇树取整行。两次 B+树下降 = 约 7~8 次 IO（各 3~4 层）。覆盖索引（查询列全部在索引中）可省掉第二步。

二级索引命中后回表：二级叶子给主键，聚簇叶子给整行。优化器代价模型（sql/opt_costmodel.cc）会把回表代价计入，行数大时宁可全表扫描。源码：InnoDB 侧 storage/innobase/row/row0sel.cc 的 row_search_mvcc() 负责按索引定位并回表；SQL 层接口在 storage/innobase/handler/ha_innodb.cc 的 index_read() / read_range_first()。

联合索引：键的顺序就是一切

联合索引 (a, b, c) 的 B+树先按 a 排序，a 相同再按 b，再按 c。因此它能直接服务：a 等值/范围、a + b、a + b + c 的查询——这就是最左前缀。但 b 或 c 单独作为条件时无法利用该索引（除非 8.0 的跳跃扫描优化，见下）。

KEY 语义

记录比较规则

索引记录按"列序"比较：先比 a，相等才比 b，以此类推。NULL 处理、字符串排序规则（collation）都会影响顺序。

cmp_data(...) 在 storage/innobase/rem/rem0cmp.cc
索引定义 dict_index_t::fields[]
每个字段含 col / prefix_len / descend

跳跃扫描（Skip Scan）

MySQL 8.0.13+：当最左列是等值条件缺失、但后续列有等值条件时，优化器可把 (a,b) 索引按 a 的不同值"跳跃"扫描。

优化器入口 test_skip_scan()
文件 sql/opt_range.cc
受 skip_scan 优化开关控制

自适应哈希索引（AHI）

AHI 不是独立索引，而是 InnoDB 在内存里为高频等值访问的 B+树页建立的哈希缓存（键 → 页内记录指针）。它透明加速 = 查询，无法主动创建、不参与优化器选路。哈希表使用分配按 innodb_adaptive_hash_index（默认 ON）控制，8.0 中每个索引分区哈希表独立管理（storage/innobase/include/ha0ha.h，hash_search()）。

05

优化器如何用索引

Execution & Optimizer

SQL 层把"怎么读"交给优化器（sql/sql_optimizer.cc）：基于统计信息估算每种访问路径的代价，选出成本最低的执行计划。访问类型从优到劣依次为 const → eq_ref → ref → range → index → ALL（EXPLAIN.type）。

访问类型阶梯

type 阶梯示意（越靠上越优）。优化器决策链：统计信息 → 估算 rows → 按代价模型排序访问方案 → 选最小代价。源码入口：Optimize_table_order() / get_best_combination()（sql/sql_optimizer.cc）。

索引下推（ICP）：把过滤下压到存储引擎

MySQL 5.6+：当 WHERE 中除索引列外还有无法完全由索引判定的条件时，在不开 ICP 的情况下，引擎只返回满足索引条件的行，服务层再过滤（大量行跨层传输）；开启 ICP 后，引擎层在读取索引记录时直接应用剩余条件，不匹配的行连回表都省了。

无 ICP

全部行上送服务层过滤

二级索引命中 1000 行 → 1000 次回表 → 服务层再逐行过滤 WHERE。回表与传输都浪费。

引擎返回 所有索引命中行
服务层 evaluate_join_record() 过滤
Extra: Using where
ICP

引擎层先过滤再回表

索引记录读出后，引擎层立即用剩余条件判断；只有通过的行才回表。回表次数从 1000 降到几十。

引擎层 row_search_mvcc() 内
应用 pushdown condition
Extra: Using index condition
源码：优化器在 sql/opt_range.cc 的 get_index_condition() 生成下推条件，InnoDB 在 storage/innobase/row/row0sel.cc 的 row_search_mvcc() 中执行 row_search_check_icp() 判断。开关 optimizer_switch='index_condition_pushdown'。

索引排序：让 ORDER BY 不 filesort

若 ORDER BY 的列序与索引键序一致（且方向一致，或全部 DESC），优化器直接沿索引叶子顺序输出，EXPLAIN 中不出现 Using filesort——省掉一次排序。这也是联合索引设计的重要考量：查询列 + 排序列尽量合成一个索引。

filesort 本身不可怕：数据量小时（优先队列排序）开销很低；真正的问题是先排序再回表的大行数场景。判断标准始终是 EXPLAIN 的 rows 与 Extra，而不是"出现 filesort 就必须建索引"。

EXPLAIN 实战解读

案例：表 user(id, name, age, email)，有 idx_age(age)、uk_email(email) 两个索引。

-- 查询 1：等值 + 范围
EXPLAIN SELECT name, age FROM user WHERE age = 30 AND name LIKE 'A%';
| id | type  | key     | rows | Extra                       |
| 1  | ref   | idx_age | 812  | Using index condition       |   ← ICP：age 定位，name 在引擎层过滤

-- 查询 2：覆盖索引
EXPLAIN SELECT age FROM user WHERE age BETWEEN 20 AND 30;
| id | type  | key     | rows | Extra                  |
| 1  | range | idx_age | 1942 | Using index            |   ← 只扫索引叶子，不回表

-- 查询 3：唯一键等值
EXPLAIN SELECT * FROM user WHERE email = 'a@b.com';
| id | type  | key      | rows | Extra |
| 1  | const | uk_email | 1    |       |   ← 唯一键等值，最多 1 行

读法：先看 type（访问方式优劣）、再看 rows（预估扫描量，乘上回表/过滤因子）、最后看 Extra 中的三个关键词——Using index（覆盖，好）、Using index condition（ICP，较好）、Using where（服务层过滤，注意）、Using filesort（额外排序，检查）。

06

索引的代价与维护

Cost & Maintenance

索引不是免费的：每棵二级索引都是一棵独立的 B+树，空间要翻倍级增长，写路径要多维护一棵树。理解代价，才能理解"索引不是越多越好"。

两类代价

空间

存储放大

每棵二级索引按"索引键 + 主键"重复存储。表越大、索引越宽、主键越长，放大越明显。主键用自增 int（4B）比 UUID（16B）省 4 倍二级索引空间。

Information_schema 统计
STATISTICS / TABLES
页数口径：data_length / page_size
写放大

每次写入多棵树

INSERT 要在每棵索引中插入记录；UPDATE 改索引列 = 删除 + 插入；DELETE 每棵树都要删除。写入热点时，二级索引是主要瓶颈。

插入路径 row_ins_index_entry_step()
删除 row_upd_del_mark_clust_rec()
文件 storage/innobase/row/row0ins.cc

页分裂与页合并

B+树的插入是在有序页中插入：页满时发生页分裂（把一半记录移到新页，父节点加一个键）；删除后页太稀疏会页合并（相邻页合并、父节点删键）。分裂/合并向上传播，是随机写放大与碎片的来源。随机主键（UUID 类）因为插入位置随机，分裂频率远高于自增主键。

实践推论：自增主键让插入永远落在"最右叶子页"，避免随机分裂；这也是"主键尽量自增/单调"的底层原因。碎片（页内利用率下降）可通过 OPTIMIZE TABLE / ALTER TABLE ... FORCE 重建，8.0 中均可在线执行。

Online DDL：重建索引不锁写

ALGORITHM机制是否复制行并发 DML说明
INSTANT仅改数据字典，秒级完成否可8.0.12+：加列/加索引的元数据操作；ADD INDEX 走 INSTANT 的场景有限，主要是加列
INPLACE原地重建（二级索引建树、表重建两阶段）二级索引：否
表重建：是		可（在线）8.0 默认；ADD INDEX / OPTIMIZE 走此路径
COPY锁表 + 逐行复制到新表是否（锁写）仅元数据不支持 INPLACE 的场景兜底

源码上，Online DDL 在 InnoDB 侧由 storage/innobase/handler/handler0alter.cc 实现：ha_innobase::inplace_alter_table() 分阶段构建索引（row_merge_build_indexes()），期间通过 ddl_log 记录增量变更，DDL 结束前回放保证一致性。8.4 中 innodb_ddl_threads 控制并行构建线程数。

统计信息与基数

优化器选路的依据是统计信息：每个索引的基数（cardinality）——"索引键的去重值数量"与表行数的比值决定区分度。InnoDB 通过随机采样页估算（storage/innobase/dict/dict0stats.cc，dict_stats_analyze_index()），结果持久化到 mysql.innodb_table_stats / mysql.innodb_index_stats。数据变化大时执行 ANALYZE TABLE 刷新，避免优化器按过期基数选错索引。

07

索引设计建议

Design Guide

设计索引没有银弹，但有可复用的决策框架。核心判断顺序：查询长什么样 → 哪些条件能走索引 → 怎么组合最少。

决策流程

① 找高频查询
慢日志 / 业务列表，按频率与耗时排序
→
② 提取过滤列
WHERE / JOIN 的等值与范围列
→
③ 设计联合索引
等值在前、范围在后；补覆盖列
→
④ EXPLAIN 验证
type / rows / Extra 三看
→
⑤ 量化收益
对比前后 rows 与耗时，去冗余

黄金规则

规则 1

高区分度优先

区分度 = 去重值 / 总行数。区分度低的列（性别、状态）单独建索引几乎无用，只适合做联合索引的前缀或末尾补充。

规则 2

最左前缀

(a,b,c) 可服务 a / a,b / a,b,c；跳列的条件无法利用。设计时把最常等值的列放最左。

规则 3

覆盖优先

高频点查尽量把 SELECT 列并入索引，让 Extra 出现 Using index，省回表。

规则 4

控制索引数

每多一棵树，写放大 +1 份。写多读少的表索引宁少勿多；一般单表不超过 5~6 个。

规则 5

主键短而单调

自增 int/bigint 优先；UUID 主键导致随机写与二级索引膨胀（8.0 可用 uuid_to_bin 转换）。

规则 6

警惕冗余

(a,b) 已存在时 (a) 是冗余；uk(email) 与 idx(email) 并存是典型浪费。

常见失效场景

写法原因正确姿势
WHERE name LIKE '%abc%'前导通配符，无法用 B+树前缀定位前缀匹配 'abc%' 可用；前导通配走全文索引
WHERE YEAR(create_time)=2024索引列套函数，键序被破坏范围写法 create_time >= '2024-01-01' AND < '2025-01-01'；或 8.0.13 函数索引
WHERE a = 1 OR b = 2单索引对 OR 只覆盖一列两个条件分别建索引（Index Merge），或改 UNION
WHERE c1 + 1 = 5索引列参与运算等号两边变换，让列保持独立：c1 = 4
WHERE v = 123（v 为 varchar）隐式类型转换（字符串↔数字）使索引失效查询常量显式加引号，列与常量类型一致
WHERE a <> 1 / a NOT IN (...)不等条件难以走索引范围数据倾斜时可拆成 a<1 OR a>1 评估
