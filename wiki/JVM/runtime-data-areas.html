运行时数据区
JVM 的内存地图

简单说：JVM 把内存切成若干区域——线程私有的程序计数器、虚拟机栈、本地方法栈，加上线程共享的堆与方法区；JDK 8 起方法区的实现从永久代换成了元空间（本地内存）。

01 运行时数据区总览 RUNTIME DATA AREAS OVERVIEW

一句话理解：按「是否被线程共享」把内存分区：私有区随线程生灭，共享区启动即建；直接内存不在规范里，但一样要防 OOM。规范本身留了极大的实现自由度。

线程私有三件套
程序计数器 · 虚拟机栈 · 本地方法栈
生命周期与线程同步：线程创建则创建、线程销毁则销毁。各线程互不影响，是「线程切换后能回到正确位置」的前提。
线程共享两件套
堆 · 方法区
虚拟机启动时创建，所有线程可见。堆是 GC 主场；方法区存放类元数据与常量池，是逻辑上的共享区域。
直接内存
本地内存 · 非规范定义
不属于《Java 虚拟机规范》定义的运行时数据区，也不应被当作「线程共享运行时数据区」；但它被频繁使用，也可能 OOM。
规范很宽松
堆可连续可不连续 · 可固定可扩展
以堆为例：堆可以是连续空间也可以不连续，大小可固定也可按需扩展；虚拟机实现可用任何 GC 算法，甚至完全不回收。
逻辑 vs 物理概念
运行时常量池/方法区/字符串常量池 = 抽象
「运行时常量池、方法区、字符串常量池是不随虚拟机实现而改变的逻辑概念；Metaspace、Heap 是与具体实现相关的物理概念」——周志明。
两次关键迁移
JDK 7 字符串池/静态变量移堆 · JDK 8 永久代→元空间
JDK 7 把字符串常量池与类静态变量从永久代移入 Java 堆；JDK 8 彻底废弃永久代，方法区实现改为本地内存中的元空间。

专题图：JDK 7 与 JDK 8 的数据区变化

两次迁移的动因不同：字符串池移堆是为了让 GC 更及时回收字符串；永久代→元空间是为了摆脱 MaxPermSize 上限并简化 GC。

02 程序计数器 PROGRAM COUNTER REGISTER

一句话理解：PC 是当前线程正在执行的字节码的「行号指示器」——解释器靠它选下一条指令，线程切换靠它恢复位置；它是规范里唯一不会 OOM 的区域。

两个核心作用
流程控制 · 线程恢复
① 字节码解释器通过改变 PC 依次读取指令，实现顺序执行、选择、循环、异常处理；② 多线程下记录当前执行位置，线程切换回来后知道上次跑到哪。
线程私有
每条线程一个 · 互不影响
为了线程切换后能恢复正确执行位置，每条线程都需要独立的计数器，独立存储——「线程私有」这个名字的由来。
执行 native 方法时
PC 值为 Undefined（未定义）
执行 Java 方法时 PC 记录当前 JVM 字节码指令地址；执行 native 方法时执行的不是字节码，PC 无意义，规范定义为 Undefined。
生命周期
随线程创建 · 随线程结束销毁
与线程完全同步：线程创建则创建，线程结束则销毁——它是运行时数据区里最小的一块内存。
唯一无 OOM 的区域
规范未规定任何 OutOfMemoryError 情况
《Java 虚拟机规范》是唯一没有为 PC 规定 OOM 情况的内存区域；规范只规定了结论，未要求所有实现采用某种固定大小的表示。
与解释执行的关系
对照 execution-engine.html 的操作数栈执行
执行引擎专题里「取指→译码→执行」循环的第一步「取指」，读的就是 PC 指向的字节码；两者配合看更完整。
03 虚拟机栈与本地方法栈 JAVA VIRTUAL MACHINE STACK

一句话理解：栈 = 栈帧的堆叠：每次方法调用压入一个栈帧，方法结束（正常或异常）就弹出。栈帧里装着局部变量表、操作数栈、动态链接与方法返回地址四件套。

线程私有 · 生命周期同线程
随线程创建而创建 · 随线程死亡而死亡
除 native 方法调用走本地方法栈外，所有 Java 方法调用都通过栈实现（与程序计数器等区域配合）。栈是运行时数据区里当之无愧的核心。
栈帧四件套
局部变量表 · 操作数栈 · 动态链接 · 返回地址
每次方法调用压入一个栈帧；方法结束后栈帧弹出。栈与数据结构中的栈一样：先进后出，只支持入栈与出栈两种操作。
局部变量表
boolean/byte/char/short/int/float/long/double + reference
存放编译期可知的基本类型与对象引用（reference 可能是指向对象起始地址的指针，也可能是句柄或其他位置）。
操作数栈
方法调用的中转站
存放方法执行过程中产生的中间计算结果与临时变量；字节码指令从局部变量表取操作数、算完再写回，详见 execution-engine 的操作数栈执行示意。
动态链接
指向运行时常量池的方法引用
每个栈帧持有指向当前方法所属类型运行时常量池的引用，把方法代码中的符号引用转换为直接引用、把变量访问转换为对应偏移；解析未定符号时可能触发类加载。
方法返回地址
正常返回 return · 异常返回（未捕获）
两种返回都会导致栈帧弹出：栈帧随方法调用创建、随方法结束销毁，无论正常完成还是异常完成都算方法结束。

专题图：栈帧结构与动态链接

栈帧四件套中，动态链接指向方法区的运行时常量池——方法调用把符号引用解析成直接引用的桥梁（注意动态分派 ≠ 动态链接）。

错误 触发条件 HotSpot 实际行为 复现手段
StackOverflowError 线程请求的栈深度超过 JVM 允许的最大深度 无限递归最常见；线程请求栈空间成功后才不会因扩展失败 OOM 无出口递归 + -Xss 调小
OutOfMemoryError 栈容量可动态扩展时，扩展申请不到足够内存 HotSpot 栈容量不可动态扩展；但线程创建时申请栈空间失败仍会 OOM 无限创建线程（-Xss 调大 + 耗尽内存）
本地方法栈 为 native 方法服务 HotSpot 中与虚拟机栈合二为一；同样可能出现两种错误 JNI 调用层过深
04 Java 堆 JAVA HEAP

一句话理解：堆是 JVM 管理的最大一块内存，几乎是所有对象与数组的分配地；按「对象活多久」分成新生代与老年代，新生代里再分 Eden 与两个 Survivor。

最大的一块 · 线程共享
虚拟机启动时创建 · GC 堆
JVM 所管理内存中最大的一块，唯一目的就是存放对象实例，几乎所有对象实例和数组都在这里分配——因此也叫 GC 堆。
「几乎」的含义
逃逸分析 · 标量替换
JIT 可基于逃逸分析做标量替换，消除部分对象的实际分配；但不能简单表述为「对象直接在 Java 虚拟机栈上分配」。
分代结构
新生代：Eden + S0 + S1 · 老年代：Tenured
分代是为了更好地回收与更快地分配：新对象进 Eden，Minor GC 后存活对象进 Survivor 并年龄 +1，达到阈值晋升老年代。
对象年龄为何 0~15
Mark Word 中 age 字段仅 4 位
年龄记录在对象头标记字段里，4 位二进制最大 1111=15，因此 -XX:MaxTenuringThreshold 上限为 15；JDK 21 上部分收集器阈值已变化。
动态年龄计算
ageTable::compute_tenuring_threshold
按年龄从小到大累加对象大小，累加到超过 Survivor 一半（TargetSurvivorRatio 默认 50%）时，取该年龄与 MaxTenuringThreshold 较小者作为新晋升阈值。
堆 OOM 的两种形态
GC Overhead Limit Exceeded · Java heap space
① JVM 花太多时间 GC 却只回收很少空间；② 创建新对象时堆中空间不足。最大堆由 -Xmx 配置，受物理内存限制。

专题图：分代结构与对象晋升

对象默认先在 Eden 分配；Minor GC 存活进 S0/S1 且年龄 +1（初始为 1），达到动态阈值后晋升老年代；大对象可能直接进老年代。

05 方法区 / 永久代 / 元空间 METHOD AREA

一句话理解：方法区是「规范概念」，永久代和元空间是它的两种 HotSpot 实现——关系像接口与实现类；JDK 8 起实现换成了本地内存中的元空间。

存储什么
类元数据 · 方法字节码 · 运行时常量池
类名、父类、接口、访问修饰符、字段与方法详情、每个方法的原始字节码指令序列、以及每个类独有的运行时常量池。
不在方法区的三类数据
静态变量 · 字符串常量池 · JIT Code Cache
静态变量与 java.lang.Class 对象一起在堆（JDK 7 起）；字符串常量池也在堆；JIT 编译后的机器码存放在独立 Code Cache 区域。
规范 vs 实现
方法区 = 抽象规范 · PermGen/Metaspace = 具体实现
《Java 虚拟机规范》只规定方法区的概念与作用，实现方式由虚拟机自行决定——类似 Java 中接口与类的关系。
为什么弃永久代
上限受限 · GC 复杂 · 合并 JRockit
① 永久代受 MaxPermSize 限制，元空间用本地内存可加载更多类；② 合并 JRockit 时对方没有永久代概念；③ 永久代 GC 复杂度高、回收效率偏低。
元空间参数
-XX:MetaspaceSize 阈值 · -XX:MaxMetaspaceSize 上限
MetaspaceSize 不是初始容量，而是触发元数据 GC 的初始高水位阈值，之后 JVM 会动态调整；不设 MaxMetaspaceSize 则只受本地内存限制。
元空间 OOM
java.lang.OutOfMemoryError: Metaspace
动态生成类（CGLIB/反射代理/热部署）最常见；可用 -XX:MaxMetaspaceSize 限制，也可用 NMT 定位谁在增长类元数据。

时间轴：永久代如何被元空间取代

HotSpot 在 JDK 6 已有放弃永久代的计划；JDK 7 先把字符串常量池与静态变量移出；JDK 8 彻底废弃，剩余内容（主要是类型信息）全部移入元空间。

JDK 6
计划期 因各方实现差异面临困难，HotSpot 团队考虑放弃永久代、改用本地内存实现方法区。
JDK 7
第一步迁移 字符串常量池与类静态变量从永久代移入 Java 堆；永久代里只剩类型信息等类元数据。
JDK 8
彻底废弃永久代 改用与 JRockit 一致的本地内存实现元空间，剩余类型信息全部移入；-XX:PermSize/-XX:MaxPermSize 失效。
JDK 14+
移除废弃参数 PermSize/MaxPermSize 等参数最终从 HotSpot 移除；方法区 = 元空间成为唯一实现（直到今天）。
06 运行时常量池与字符串常量池 CONSTANT POOLS

一句话理解：Class 文件里有一张常量池表（字面量 + 符号引用），类加载后搬进方法区的运行时常量池；字符串常量池是另一回事——JDK 7 起在堆里，专门缓存字符串避免重复创建。

常量池表 → 运行时常量池
类加载后存放于方法区
Class 文件除版本、字段、方法、接口描述外，还有存放字面量与符号引用的常量池表；类加载后整体搬入方法区的运行时常量池。
字面量 vs 符号引用
Literal · Symbolic Reference
字面量：整数、浮点数、字符串字面量等源代码固定值；符号引用：类、字段、方法、接口方法的符号引用。
符号引用 vs 直接引用
符号引用与内存布局无关 · 直接引用指向目标
符号引用用字面量描述目标、不依赖实现布局；直接引用是指针/相对偏移/句柄，与具体虚拟机内存布局直接相关，目标必定已加载。
字符串常量池
避免字符串重复创建 · intern
针对 String 专门开辟的区域：字面量 "ab" 先查池，没有则创建放入，再返回引用——`aa==bb` 为 true；new String 则每次新建对象。
StringTable 实现
src/hotspot/share/classfile/stringTable.cpp
现代 HotSpot 用并发哈希表 + 弱句柄保存堆中的字符串对象，支持扩容、重哈希、清理失效条目；-XX:StringTableSize 设初始桶数。
为何 JDK 7 移入堆
永久代 GC 回收效率太低
永久代的字符串只在整堆收集（Full GC）时才被回收；程序中有大量字符串等待回收，放进堆能让 Minor GC 及时处理。
07 直接内存与堆外内存 DIRECT MEMORY

一句话理解：直接内存在本地内存中分配，不是规范定义的运行时数据区；NIO 用它减少一次复制，但它的上限受本机总内存与寻址空间约束，照样会 OOM。

NIO 与直接缓冲区
Channel + Buffer · DirectByteBuffer
JDK 1.4 引入 NIO：直接字节缓冲区在 Java 堆外分配，通过堆中的 DirectByteBuffer 对象操作；JVM 尽力直接在其上执行本地 I/O，减少中间缓冲复制。
NIO ≠ 非阻塞
只有 Selector 等部分提供非阻塞 I/O
不能把整个 NIO 展开为 Non-Blocking I/O——只有可选择通道与 Selector 等部分提供非阻塞能力，其余仍是阻塞 I/O。
限制与参数
-XX:MaxDirectMemorySize
直接内存不计入 Java 堆，但仍受本机总内存与处理器寻址空间限制；NIO 直接缓冲区可通过该参数限制总分配量。
堆外内存 ≠ 直接内存
堆外是统称 · 直接内存是其中一种
堆外内存是「Java 堆之外内存」的统称，底层通常用本地内存；是否受 JVM/JDK 管理取决于分配方式，把两者直接划等号并不准确。
清理机制
DirectByteBuffer 不可达 → Cleaner
直接缓冲区的本地内存关联堆中对象，对象不可达后通过 Cleaner 机制参与清理；清理时机不受应用控制，需警惕本地内存泄漏与 OOM。
为什么用直接内存
减少一次复制 · 减轻堆压力
网络/文件读写可避免「堆内→堆外」的中间拷贝；大数据量 I/O 场景收益明显，但要为内存上限与回收时机买单。
08 HotSpot 对象探秘 OBJECT CREATION & LAYOUT

一句话理解：new 一个对象要过五道工序——类加载检查 → 分配内存 → 初始化零值 → 设置对象头 → 执行 <init>；面试能默写这五步，就算吃透对象创建。

专题图：对象创建五步流水线

从 new 指令到可用对象：前四步是「虚拟机的视角」，第五步执行 后才是「Java 程序视角」的完整对象。

专题图：对象内存布局

对象在堆中的布局 = 对象头（Mark Word + Klass 指针）+ 实例数据 + 对齐填充；启用压缩类指针时对象头常见 12 字节。

访问方式 原理 优点 HotSpot 的选择
句柄访问 堆中划句柄池，reference 存句柄地址；句柄内含实例数据与类型数据的地址 对象被移动时只需改句柄中的实例数据指针，reference 本身不变——GC 搬运对象友好 非主流
直接指针 reference 中直接存储对象地址，对象内再含指向类型数据的指针 速度快，省去一次指针定位的时间开销 HotSpot 主要使用
分配细节 指针碰撞（堆规整，Serial/ParNew）vs 空闲列表（堆不规整，CMS） 规整性由 GC 是否带压缩整理决定；复制算法也规整 并发用 CAS+重试 / TLAB
09 验证实验：亲手看内存 VERIFY WITH TOOLS

一句话理解：把每个区域「打爆」一次，错误信息就是最好的教材——栈溢出、元空间溢出、字符串池 intern、直接内存限制，一次实验一个结论。

栈溢出 · StackOverflowError
java -Xss256k StackOverflowDemo
# Exception in thread "main"
# java.lang.StackOverflowError
无限递归（或递归过深）压爆栈；把 -Xss 从默认改到 256k，同一递归深度更早崩溃，直观感受「栈深度有限」。
元空间溢出 · Metaspace
java -XX:MaxMetaspaceSize=16m \
     -XX:MetaspaceSize=16m MetaSpaceDemo
# java.lang.OutOfMemoryError: Metaspace
循环用 CGLIB/反射生成新类，把类元数据塞爆元空间；限制 MaxMetaspaceSize 后立刻复现 OOM，验证「元空间不是无限」。
字符串池 · intern 行为
String a = "ab";
String b = new String("a") + new String("b");
System.out.println(a == b);        // false
System.out.println(a == b.intern());// true
JDK 7 后 intern 返回池中引用（未命中则入池）；字面量进池时机与常量池表相关，是面试高频题，跑一遍比背结论牢。
直接内存 · MaxDirectMemorySize
java -XX:MaxDirectMemorySize=8m \
     -XX:+ExitOnOutOfMemoryError DirectMemDemo
# OutOfMemoryError: Direct buffer memory
循环 ByteBuffer.allocateDirect 不释放；参数压到 8m 快速复现「Direct buffer memory」OOM，理解直接内存独立于堆。
对象头观测 · JOL
# 依赖 org.openjdk.jol:jol-core
java -jar jol-cli.jar internals \
     -cp . org.example.User
打印对象布局：对象头字节数（含压缩指针）、实例字段偏移、对齐填充——亲眼看到 Mark Word/Klass 指针/12 字节头部。
内存全景 · NMT
java -XX:NativeMemoryTracking=summary \
     -XX:+UnlockDiagnosticVMOptions \
     -XX:+PrintNMTStatistics -version
Native Memory Tracking 按区域汇总：堆、元空间、Code Cache、线程栈、GC 等各占多少，调优与排查本地内存泄漏的起点。
