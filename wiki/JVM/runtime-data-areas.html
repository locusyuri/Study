运行时数据区
JVM 的内存地图

简单说：JVM 把内存分成「线程私有的草稿纸」（PC、虚拟机栈、本地方法栈）和「线程共享的大仓库」（堆、方法区）。谁用什么区域、区域里装什么、装满了抛什么异常，就是本页的全部内容。

PC · 栈 · 本地方法栈

GC 主战场 · 生命周期最长

直接内存

01 线程私有区 THREAD-PRIVATE AREAS

一句话理解：每个线程都有自己独立的三块「草稿纸」，互不共享、随线程生灭、不参与 GC。它们回答的问题是：这条线程现在执行到哪、调用栈有多深、本地方法栈在哪。

程序计数器 PC
java.lang.Thread · HotSpot: runtime/thread.cpp
记录当前线程正在执行的字节码行号（native 方法时为 undefined）。线程切换后靠它恢复位置，是「线程怎么知道自己跑到哪」的答案。唯一不会 OOM 的区域。
虚拟机栈 JVM Stack
java.lang.StackOverflowError · -Xss256k
每次方法调用压入一个栈帧（Frame）。栈深度超限抛 StackOverflowError；栈空间可扩展但通常固定。-Xss 控制单线程栈大小，递归越深占用越大。
本地方法栈
jdk.internal.misc.Unsafe · native 方法
为 native（C/C++）方法服务。HotSpot 实现中与虚拟机栈合并；Unsafe 的本地内存操作、JNI 调用都经过这条路径。
栈帧 Frame
HotSpot: runtime/frame.cpp
方法执行的完整上下文：局部变量表 + 操作数栈 + 动态链接 + 返回地址（见下方专题图）。jstack 打印的每行 = 一个栈帧。

专题图：一个栈帧的内部结构

方法从调用到返回，栈帧承载全部执行状态。自上而下是编译期可确定与运行期动态两大部分。

02 Java 堆 JAVA HEAP

一句话理解：堆是「对象的大仓库」：新建对象先到 Eden，躲过几次 GC 就晋升老年代。它是 GC 的主战场，也是内存调优最先看的地方。

Eden / Survivor / Old
-XX:SurvivorRatio=8
新生代 = Eden + S0 + S1（默认 8:1:1）。新对象进 Eden；Minor GC 后存活对象在 S0/S1 间复制，S 区始终保留一个空的。
对象晋升
-XX:MaxTenuringThreshold=15
每躲过一次 Minor GC 年龄 +1（对象头 Mark Word 存年龄），达到阈值晋升老年代；大对象（-XX:PretenureSizeThreshold）直接进老年代。
堆大小参数
-Xms / -Xmx / -Xmn
初始堆 / 最大堆 / 新生代大小。生产建议 -Xms = -Xmx 避免扩容抖动；-Xmn 控制新生代占比，过大挤压老年代、过小频繁 Minor GC。
分配路径
HotSpot: gc/shared/collectedHeap.cpp · TLAB
优先 TLAB（线程本地分配缓冲，无竞争）→ 失败走 CAS 分配 → Eden 放不下则直接尝试老年代。理解这条链，才能理解「为什么有的对象直接进老年代」。
堆与收集器
-XX:+UseG1GC（JDK 9+ 默认）· -XX:+UseParallelGC
Parallel 下堆按分代物理连续；G1 起堆切成 Region（约 2048 个），逻辑分代、物理不连续，停顿可预测。堆「长什么样」取决于收集器。
堆溢出 OOM
java.lang.OutOfMemoryError: Java heap space
对象分配不下时抛出。排查三件套：-XX:+HeapDumpOnOutOfMemoryError 自动转储 → MAT 分析支配树 → 定位泄漏对象与引用链。

专题图：对象在堆里的旅程（分代 + 晋升）

默认 Parallel/分代模型示意；G1 为 Region 化实现，逻辑分代一致。箭头 = 对象移动路径。

03 方法区 / 元空间 METHOD AREA & METASPACE

一句话理解：方法区装「类本身的信息」而不是对象：类元数据、运行时常量池、方法字节码。JDK 8 起它从堆里的永久代搬到本地内存，改名 Metaspace。

Metaspace 内容
java.lang.Class · HotSpot: memory/metaspace/
类元数据（Klass 结构）、运行时常量池、字段/方法信息、方法字节码、类加载器引用。静态变量 JDK 7 后已移入堆，注意与「类信息」区分。
为什么弃永久代
JEP 122：PermGen 移除
永久代大小难估、与堆耦合、回收脆弱；改为本地内存后 Metaspace 默认可无限增长（受物理内存限制），且字符串常量池移入堆。
元空间参数
-XX:MetaspaceSize · -XX:MaxMetaspaceSize
MetaspaceSize 是触发 GC 的初始阈值（不是上限）；MaxMetaspaceSize 设硬上限，超限抛 OOM: Metaspace。动态生成类的场景（反射、CGLIB）尤其要关注。
运行时常量池
HotSpot: oops/constantPool.hpp
类文件常量池（CONSTANT_Class/Methodref/Utf8…）的运行时版本，存字面量与符号引用；动态链接阶段在此完成「符号 → 直接引用」替换。
类加载器与泄漏
java.lang.ClassLoader · OOM: Metaspace
类由加载器 + 类名唯一定位；反复创建加载器（如热部署、反射框架）且无法卸载 → 元空间持续增长，是 Metaspace OOM 的头号原因。

演进时间轴：PermGen → Metaspace

同一份「类信息」的存放位置与治理方式，随 JDK 演进发生了两次关键变化。

JDK 6/7
永久代 PermGen 方法区位于堆内永久代；-XX:PermSize / -XX:MaxPermSize 控制。字符串常量池也在永久代，是「常量池 OOM」重灾区。
JDK 8
元空间 Metaspace 取代永久代 JEP 122：方法区移入本地内存，默认无上限（可设 -XX:MaxMetaspaceSize）；字符串常量池与静态变量移入 Java 堆。OOM 类型从 PermGen space 变为 Metaspace。
JDK 9+
模块化与治理完善 JPMS 模块描述符进入常量池解析；Metaspace 内部按 ClassLoaderData 分块管理、支持卸载统计；G1 默认收集器下的类卸载由并发周期承担。
04 字符串常量池与直接内存 STRING POOL & DIRECT MEMORY

一句话理解：字符串常量池是堆里的「字符串去重仓库」，直接内存是堆外的「零拷贝快递通道」。一个管命中、一个管性能，都是高频踩坑点。

字符串常量池
java.lang.String · String.intern()
JDK 7 起位于堆中，存字面量（""）与 intern() 结果。判断「==」先问：是池里的同一对象吗？频繁 intern 大字符串会撑大堆。
编译期与运行期
javac 常量折叠 · StringBuilder 拼接
"a"+"b" 编译期折叠为 "ab" 进池；含变量的拼接走 StringBuilder/indy（JDK 9+ 字符串拼接指令）——解释「为什么字符串拼接别用 +」的底层原因。
直接内存
java.nio.ByteBuffer.allocateDirect
堆外内存，读写少一次堆内拷贝，Netty 与 NIO 零拷贝的基础。-XX:MaxDirectMemorySize 限制总量（默认≈-Xmx），Full GC 时回收 DirectByteBuffer。
堆外泄漏特征
OOM: Direct buffer memory
堆看起来很小、进程 RSS 却很大，或反复 Full GC 仍涨——多半是直接内存泄漏（DirectByteBuffer 未被 GC 或未调用 cleaner）。用 -XX:MaxDirectMemorySize 收口排查。
05 异常与参数速查 EXCEPTIONS & PARAMETERS

一句话理解：每个区域都有对应的「装满了」的报错，和对应的控制参数。看到异常先定位区域，再查参数与排查手段——这是排查的第一步。

异常 区域 触发场景 相关参数 排查方向
StackOverflowError 虚拟机栈 方法递归过深、无限递归，栈深度超限 -Xss jstack 看栈顶方法，查递归/深调用链
OOM: Java heap space 堆 对象分配不下：泄漏或峰值内存超 -Xmx -Xms / -Xmx HeapDump + MAT 分析支配树、引用链
OOM: Metaspace 方法区 类元数据耗尽：动态生成类、热部署加载器泄漏 -XX:MetaspaceSize
-XX:MaxMetaspaceSize		 jcmd GC.class_stats 看类占用，查加载器
OOM: Direct buffer memory 直接内存 DirectByteBuffer 堆积、未及时回收 -XX:MaxDirectMemorySize 统计 DirectBuffer 数量，查未释放的 NIO 缓存
OOM: GC overhead limit exceeded 堆 GC 回收效率过低（98% 时间回收 <2% 空间） -XX:+UseG1GC 等收集器 本质是堆太小/泄漏，先转储再调参
06 验证实验：用工具看内存 VERIFY WITH TOOLS

一句话理解：纸上谈兵不如一行命令。下面的命令可以直接在本地 JDK 21 上跑，把「区域大小」变成真实数字。IDE 终端或命令行均可。

jcmd · 查看 JVM 参数
jcmd <pid> VM.flags
jcmd <pid> VM.system_properties
确认 -Xmx、MetaspaceSize 等实际生效值（含默认值），是所有调优的第一步。先 jps 拿到 pid。
jmap · 堆概览与转储
jmap -heap <pid>
jmap -dump:format=b,file=heap.hprof <pid>
-heap 看新生代/老年代容量与使用率；-dump 做堆转储交给 MAT。生产环境优先用 jcmd GC.heap_dump 替代。
jstat · GC 与类加载统计
jstat -gc <pid> 1000
jstat -class <pid>
每秒采样一次 GC 次数与耗时、各代容量（EU/OU）；-class 看加载类数量，辅助判断 Metaspace 压力。
制造现场 · 触发各区域异常
java -Xss160k StackOverflowDemo
java -Xmx64m OOMDemo
java -XX:MaxMetaspaceSize=64m MetaDemo
写最小复现类分别触发 StackOverflow / heap OOM / Metaspace OOM，配合 -XX:+HeapDumpOnOutOfMemoryError 留档，走一遍完整排查流程。
jhsdb · 深入运行时
jhsdb jmap --heap --pid <pid>
jhsdb jstack --pid <pid>
JDK 9+ 的底层调试工具，能看更细的运行时结构；需要时用，日常 jcmd/jstat 已覆盖多数场景。
-Xlog · GC 与类加载日志
-Xlog:gc*:file=gc.log
-Xlog:class+load,class+unload
JDK 9+ 统一日志框架：gc* 记录各代回收与停顿；class+load/unload 记录类加载/卸载，定位「谁在制造类」。

从「画地图」到「看数字」：先建立六大区域的静态认知，再用工具把它变成动态观测。JDK 标准库类可在 IDE 里直接看 src.zip。

背下全景图

线程私有：PC/虚拟机栈/本地方法栈；线程共享：堆/方法区；外加直接内存。先分清「谁私有的、谁共享的」。

搞懂栈帧

局部变量表 → 操作数栈 → 动态链接 → 返回地址；再配合递归写一个 StackOverflowError，体会 -Xss 的作用。

3
搞懂堆分代

Eden/S0/S1/Old 与晋升路径 → 写循环 new 对象触发 Minor GC，用 jstat -gc 观察各代使用率变化。

4
搞懂方法区

Metaspace 内容与演进 → 反射/CGLIB 动态生成类制造 OOM: Metaspace，用 jcmd GC.class_stats 定位。

5
对照源码

IDE 里看 java.lang.Thread、java.nio.ByteBuffer；HotSpot 路径（thread.cpp / frame.cpp / constantPool.hpp）在线浏览对照。
