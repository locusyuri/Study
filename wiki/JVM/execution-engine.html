执行引擎与字节码
JVM 怎么把代码跑起来

简单说：字节码先被解释器逐条翻译执行，跑热的方法再被 JIT 编译成机器码直接执行。两条通道的目标一致——把「跨平台的中间码」变成「这台 CPU 能跑的本机指令」。

输入
方法字节码
约 200+ 条指令 · 栈式
双通道
解释 + JIT
C1 / C2 分层编译
输出
机器码
当前 CPU 原生指令
01 字节码与指令集 BYTECODE & INSTRUCTION SET

一句话理解：javac 把 Java 方法编译成一串字节码指令，全部基于「操作数栈」运算——指令不直接操作寄存器，而是往栈上压值、从栈上取值。这是跨平台的关键设计。

指令分类
javap -c 反汇编
加载/存储（iload/istore）、运算（iadd）、类型转换、对象创建（new）、字段访问（getfield）、方法调用（invoke*）、控制转移（if/goto）、异常、同步（monitorenter）。
栈式指令模型
操作数栈深度编译期已定
一条 iadd 弹出两个 int、压入一个 int；指令天然紧凑（多为 1 字节 opcode），JVM 不需要知道寄存器布局——平台无关性的来源。
方法描述符
(II)I · (Ljava/lang/String;)V
常量池里用描述符编码签名：参数类型+返回类型。invokevirtual 靠「常量池索引 + 描述符」找到目标方法——解析阶段的主角。
局部变量表槽位
istore_1 · aload_0
this 占 index 0；long/double 占两个槽位；指令集为前 4 个槽位提供无操作数快捷形式（iconst_0~5、istore_0~3）。
异常表
javap -v · Exception table
try-catch 编译为异常表条目（起始/结束/处理器偏移 + 捕获类型），异常抛出不靠 if，靠查表匹配处理器。
读字节码工具链
javap · ASM · Byte Buddy · CFR 反编译
javap 看官方字节码；ASM 读写（框架底层）；Byte Buddy 运行时生成；CFR 反编译回 Java——四件套覆盖「读-改-造-还原」。

左侧为 javap 反汇编结果；右侧三步展示操作数栈与局部变量表的变化。箭头 = 栈顶方向。

02 解释执行 INTERPRETATION

一句话理解：解释器是「逐条翻译」的执行者：每执行一条字节码，都要经历取指 → 解码 → 执行。它不产生编译缓存，胜在启动快、实现简单。

解释循环
HotSpot: interpreter/bytecodeInterpreter.cpp
主循环 while：取 opcode → 查分发表 → 执行对应处理逻辑 → 更新 PC。每条指令一小段 C++ 逻辑，语义直观、无预热代价。
模板解释器
interpreter/templateTable.cpp
HotSpot 的优化：启动时为每条字节码生成一小段机器码模板，解释执行变成「跳进模板跑机器码」——比纯 C++ 循环快一个量级。
栈帧切换
interpreter/ · 解释帧 vs 编译帧
解释帧与 JIT 编译帧布局不同，方法调用需「桥接」（i2c/c2i 适配器）。混合执行时频繁切换有开销，是「逃逸分析 + 内联」能省掉的成本之一。
-Xint / -Xcomp / -Xmixed
运行模式开关
-Xint 纯解释（验证语义）；-Xcomp 强制编译（关闭热点，启动即全编译）；-Xmixed 混合（默认）。对比三者的启动与吞吐，直观感受解释 vs JIT。
03 JIT 编译与分层编译 JIT & TIERED COMPILATION

一句话理解：JIT（Just-In-Time）只在「热点方法」被调用足够多次后才编译。现代 HotSpot 用 C1（快、带 profiling）和 C2（慢、极优化）分层协作。

0
解释执行 · 启动默认
无编译 · 启动即用
1
C1 简单编译 · 无 profiling
-XX:TieredStopAtLevel=1 只到这层
2
C1 有限 profiling · 收集调用信息
方法计数器 + 分支计数器
3
C1 完全 profiling · 全量采集
为 C2 决策提供画像
4
C2 编译 · 激进优化
-XX:CompileThreshold 触发 · 最终形态
热点探测
runtime/compilationPolicy.cpp
方法调用计数器 + 回边计数器（循环次数）：方法被调用/循环执行超过阈值即判定热点。-XX:CompileThreshold 默认 10000（C2）。
C1 编译器
HotSpot: c1/
客户端编译器：编译快、优化适度，同时采集 profiling 信息（分支走向、类型、去优化点）。第 1~3 层。
C2 编译器
c2/ · -XX:MaxInlineSize
服务端编译器：基于 profiling 做激进优化（内联、逃逸分析、向量化、循环变换）。编译耗时但执行最快，第 4 层。
Graal / AOT
GraalVM · Native Image · -XX:+UseJVMCICompiler
Graal 是 Java 写的 JIT（可替代 C2）；AOT（提前编译）把字节码预编译成镜像，启动毫秒级但失去动态优化——执行引擎的两条分支路线。
Code Cache
-XX:ReservedCodeCacheSize
机器码存放区，满了会退化（停止编译回解释）。-XX:+PrintCodeCache 观察占用；大型应用常需调大预留。
去优化
deoptimize · uncommon trap
编译假设被打破（如突然出现新子类、类型画像变化）时，把执行回退到解释器重新走——C2 激进优化的「后悔药」，保证正确性兜底。
04 JIT 核心优化 KEY OPTIMIZATIONS

一句话理解：C2 的优化分两类——消除「调用成本」（内联）和消除「对象成本」（逃逸分析）。看懂这两个，就理解了「为什么 Java 也能跑得很快」。

方法内联
-XX:MaxInlineSize=35 · -XX:MaxInlineLevel=9
把被调方法体展开到调用处：省掉调用开销，让后续优化「看得更远」。getter/setter、小方法几乎必内联；大方法/虚调用受限。
逃逸分析
c2/escapeAnalysis.cpp · -XX:+DoEscapeAnalysis
证明对象不逃逸方法作用域后：栈上分配（省 GC）、标量替换（拆成字段）、锁消除（省同步）。JDK 里大量「局部小对象」因此零堆分配。
锁消除与粗化
c2/ · 逃逸分析衍生
对象不逃逸 → 去掉 synchronized；相邻同步块合并（粗化）减少加锁次数。StringBuffer、局部集合的同步往往被这样优化掉。
类型特化
profile 驱动 · 单态/双态调用点
基于 profiling 假设调用点只有一种实现，去虚化（把 invokevirtual 变成直接调用）；错了就去优化回退。虚调用不再「天生慢」。
循环与代数优化
c2/loopopts.cpp
循环展开、循环不变量外提、公共子表达式消除、强度削减（乘法→移位）。CPU 密集代码的主要加速来源。
向量化
SuperWord · -XX:+UseSuperWord
把标量循环转成 SIMD 向量指令（AVX 等），数组求和/拷贝类代码提速数倍；部分场景可用 Vector API（jdk.incubator.vector）显式表达。
05 invokedynamic 与 MethodHandle INVOKEDYNAMIC & METHOD HANDLE

一句话理解：普通方法调用在编译期就定死了调用点，invokedynamic 把「怎么调用」推迟到运行期由引导方法决定——语言特性的后门。

调用点 Call Site
java.lang.invoke.CallSite · ConstantCallSite
invokedynamic 指令执行时，先调引导方法（bootstrap method）生成 CallSite，CallSite 持有目标 MethodHandle，之后按句柄调用。
引导方法
BootstrapMethods 属性 · LambdaMetafactory
常量池存 BootstrapMethods 表；Lambda 表达式由 LambdaMetafactory 引导生成实现类与句柄，String 拼接（JDK 9+）由 StringConcatFactory 引导。
MethodHandle
java.lang.invoke.MethodHandles.Lookup
「可传递的方法指针」：类型签名 + 句柄绑定；比反射更快（编译期可优化），是框架层替代反射的新选项。
为什么需要它
JSR 292 · 动态语言/特性支持
Lambda、模式匹配、序列化、动态代理、字符串拼接……都靠它把「语言语义」翻译成「JVM 语义」，且不牺牲 JIT 优化（调用点可被去虚化）。
06 观测编译产物 OBSERVING COMPILATION

一句话理解：JIT 是黑盒，但 PrintCompilation 能把「谁被编译了、为何内联失败」变成日志。性能归因的第一步，就是看编译日志。

PrintCompilation
-XX:+PrintCompilation
每行一条编译记录：时间戳、方法、编译层、大小、是否 OSR（循环内编译）。观察「哪些方法进了第 4 层」。
PrintInlining
-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining
内联决策树：谁内联进谁、因「方法太大/调用点太热/接口调用」等被拒绝——回答「为什么这行代码慢」的利器。
JITWatch
AdoptOpenJDK 开源工具 · 解析编译日志
把 PrintCompilation/PrintInlining 输出可视化：源码↔字节码↔汇编 三栏对照，看一段代码最终编译成了什么。
-XX:+PrintAssembly
需 hsdis 插件 · 反汇编机器码
直接看 JIT 生成的汇编（含注释标注源行），向量化/标量替换一目了然；需要下载 hsdis-amd64 放入 JDK bin。
07 验证实验：亲手看 JIT VERIFY WITH TOOLS

一句话理解：写一个会被反复调用的方法，用 PrintCompilation 亲眼看到它从解释进入 C2。看一次编译日志，胜过背十遍理论。

javap · 读自己的字节码
javap -c -p MyClass.class
javap -v MyClass.class
-c 看指令序列、-v 看常量池与异常表。找一个写过的类，把「源码 → 字节码」对应起来。
PrintCompilation · 看编译发生
java -XX:+PrintCompilation HotDemo
热循环跑几秒后刷新日志：方法名后出现第 2/3/4 层编译记录；对每个方法观察「从解释到 C2」的升级过程。
PrintInlining · 看内联决策
java -XX:+UnlockDiagnosticVMOptions \
     -XX:+PrintInlining HotDemo
getter/setter 应显示 @ inline 成功；大方法显示 too big / callee too big。对照 -XX:MaxInlineSize 调整验证。
-Xint vs 默认 · 体感差距
java -Xint HotDemo
java HotDemo
同一段热循环：-Xint 纯解释明显更慢；默认混合模式跑起来后大幅提速——解释 vs JIT 的直观对比实验。
对象分配观测 · 逃逸分析生效
java -Xlog:gc -Xmx128m EscapeDemo
循环里 new 一个不逃逸的 Point：GC 日志几乎无分配压力；改用 -XX:-DoEscapeAnalysis 关闭后立刻开始频繁 GC——标量替换的实证。
JITWatch · 可视化编译
java -XX:+UnlockDiagnosticVMOptions \
  -XX:+PrintCompilation -XX:+PrintInlining \
  -XX:+PrintAssembly -XX:LogFile=jit.log HotDemo
导出完整日志喂给 JITWatch，在「源码/字节码/汇编」三栏里追踪一个方法的完整编译旅程。
建议阅读路径

从「看得懂字节码」到「看得懂编译日志」：先用 javap 建立指令直觉，再用 PrintCompilation 建立 JIT 直觉，最后读优化原理与源码。

1
读懂字节码

javap -c 反汇编一个类：操作数栈模型、方法描述符、异常表；写 if/循环/异常案例对照。

2
体感解释 vs JIT

-Xint 与默认模式跑同一热循环对比耗时；-verbose:class 之外再开 -XX:+PrintCompilation 看编译发生。

3
理解分层编译

C1/C2 各层职责与触发阈值 → 观察方法逐层升级 → 用 -XX:TieredStopAtLevel 限制层次对比性能。

4
吃透两大优化

方法内联（PrintInlining 验证）→ 逃逸分析（EscapeDemo + GC 日志验证）→ 类型特化与去优化。

5
认识 invokedynamic

javap -v 看 Lambda 的 BootstrapMethods → 读 java.lang.invoke 源码 → 理解 StringConcatFactory。

6
回到总览

回 OVERVIEW.html，把执行引擎放回「类加载 → 内存 → 执行 → GC」链路；对照 class-loading.html 看字节码从哪里来。
