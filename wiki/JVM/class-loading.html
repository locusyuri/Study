类加载机制
字节码进入 JVM 的入口

简单说：.class 文件只是一张「蓝图」，类加载器负责找到它，五阶段负责把它变成可用的 Class 对象——加载、验证、准备、解析、初始化。谁负责找、怎么找、找到后做什么，就是本页的内容。

01 类加载器体系 CLASS LOADER HIERARCHY

一句话理解：JVM 里的类不是「读进来」的，而是被某个类加载器「定义」出来的。类由「加载器 + 全限定名」共同唯一确定，这就是为什么同名类可以共存。

Bootstrap 启动类加载器
C++ 实现 · getClassLoader() 返回 null
JVM 自身的一部分，加载 java.base 等核心模块（rt.jar 的现代版）。用 C++ 实现，Java 侧拿不到引用，所以显示为 null。
Platform 平台类加载器
java.lang.ClassLoader · JDK 9 更名
由 Extension（扩展）加载器改名而来。加载 java.base 之外的标准模块（java.sql、java.xml 等），是 Bootstrap 的子级。
Application 应用类加载器
AppClassLoader · classpath / -cp
加载 classpath 上的用户类与第三方依赖，默认的「我们写的类」的加载者，也是线程上下文类加载器的默认值。
自定义类加载器
继承 ClassLoader · 覆写 findClass()
模板方法模式：loadClass() 已实现委派逻辑，子类只需覆写 findClass() 返回字节（defineClass）。热部署、加密类、字节码增强都靠它。
核心方法三件套
loadClass · findClass · defineClass
loadClass 实现双亲委派；findClass 由子类实现「去哪找」；defineClass 把字节数组变成 Class。加 findLoadedClass 检查缓存。
命名空间隔离
ClassLoader 实例 + 类名 = 类身份
不同加载器加载的「同名类」互不兼容（instanceof 为 false）。这是 Tomcat 应用隔离、OSGi 模块化的根基。

专题图：双亲委派模型

类加载请求自底向上逐级委托，实际加载自顶向下逐级回落。核心保证：任何类最多被加载一次，核心 API 只属于 Bootstrap。

02 五阶段生命周期 CLASS LIFE CYCLE

一句话理解：加载是「找到蓝图」，验证是「验真伪」，准备是「备空间」，解析是「连符号」，初始化才是「动真格」。前四步懒散、第五步由主动使用触发。

① 加载 Loading
读字节流（classpath/JAR/网络）→ 解析为方法区结构 → 生成 Class 对象
产物：Class 对象（堆）
ClassNotFoundException
② 验证 Verification
四关：文件格式（魔数/版本）→ 元数据（父类/类型）→ 字节码（栈帧/类型安全）→ 符号引用
产物：通过校验
VerifyError / ClassFormatError
③ 准备 Preparation
为静态字段分配内存并赋「零值」——不是代码里的初值；final static 常量已在常量池
产物：零值静态变量
—
④ 解析 Resolution
符号引用 → 直接引用（内存地址/偏移）；可延迟到首次使用（lazy resolution）
产物：直接引用
NoSuchFieldError / NoSuchMethodError
⑤ 初始化 Initialization
执行 <clinit>：静态块 + 静态字段赋值；唯一「主动使用」触发的阶段
产物：类就绪可用
ExceptionInInitializerError
主动使用六种触发
new · getstatic · putstatic · invokestatic
创建实例、读写静态字段（非常量）、调用静态方法、反射（Class.forName）、初始化子类（先父后子）、作为 main 入口类。满足其一即触发初始化。
被动引用不触发
子类引用父类静态字段 · 数组定义 · 常量
「引用父类静态字段」只初始化父类不初始化子类；new 数组只初始化数组类；引用编译期常量（final static）直接取常量池值，不触发类初始化。
加载的唯一性与缓存
findLoadedClass · 加载器+类名
同一个加载器下同名类只加载一次；再次请求命中缓存。这是「为什么重复 new 不重复加载类」的原因。
接口与特殊规则
JLS §12.4 · 接口初始化
接口初始化不触发父接口初始化（除非父接口静态字段被使用）；方法句柄（invokedynamic）调用点也会触发目标类初始化。
卸载条件
HotSpot: classfile/systemDictionary.cpp
类加载器可被回收 + 类无实例 + 类无引用三条件齐备才卸载；自定义加载器场景（热部署）是理解元空间回收的关键。
观察加载序列
java -verbose:class Demo
启动时打印每行「[Loaded xxx from ...]」，真实看到「先父后子」的加载顺序与懒加载：用到哪个类才加载哪个。
03 常量池与符号引用 CONSTANT POOL & SYMBOLIC REFERENCE

一句话理解：.class 里全是「名字」（符号引用），运行期才把名字翻译成「地址」（直接引用）。这一层间接，是 JVM 支持动态绑定与热替换的根基。

类文件常量池
javap -v · CONSTANT_* 表项
CONSTANT_Class / Utf8 / Methodref / Fieldref / String / Integer…：编译期生成，全是「符号」——类名、方法名、字段名、描述符。
运行时常量池
HotSpot: oops/constantPool.hpp
类文件常量池进入方法区后的运行时版本：部分表项已解析为直接引用（方法指针、字段偏移），未用到的保持符号态。
解析 vs 延迟
-XX:+AlwaysResolveClassConstants（调试用）
默认 lazy：符号引用在首次使用时才解析（解析阶段），失败抛 NoSuchFieldError 等；反射与 MethodHandle 有各自的解析路径。
字符串常量与 intern
CONSTANT_String · String.intern()
类文件里的字符串字面量以 CONSTANT_String 存在，类加载后首次使用时 intern 进堆中的字符串常量池——回到运行时数据区专题的呼应点。
04 打破双亲委派：SPI 与容器 BREAKING PARENT DELEGATION

一句话理解：双亲委派默认「父先来」，但有些场景必须「父问子要」或「各自为政」。理解反例，才是真正理解双亲委派。

SPI 问题：JDBC
java.sql.DriverManager · ServiceLoader
DriverManager 由 Bootstrap 加载，却要调用 App 加载的 MySQL 驱动——父加载器看不到子加载器的类。解法：线程上下文类加载器（TCCL）反向委托。
TCCL 线程上下文类加载器
Thread.setContextClassLoader()
每个线程可设置自己的类加载器，让「上层代码」用「下层类加载器」加载实现类。ServiceLoader 的默认加载器，SPI 落地的钥匙。
Tomcat 容器隔离
WebAppClassLoader · 每应用一个
每个 Web 应用独立类加载器：先自己加载再委派父级（打破顺序），同名类库互不干扰，支持热部署（换加载器即换类）。
覆写 loadClass 全打破
自定义 ClassLoader 覆写 loadClass()
完全绕过委派逻辑（如 OSGi 的模块间依赖委托）。代价：核心类一致性风险，需自己保证「不该打破的不打破」。
JDK 9+ 的变化
模块化下的扁平层级 · 可读性图
模块系统让「谁依赖谁」显式化（requires），部分 SPI 场景被模块导出/开放替代；但 TCCL 与容器隔离仍是主流实践。
05 JPMS 模块化 JAVA PLATFORM MODULE SYSTEM

一句话理解：JDK 9 给「类 + 包」之上加了一层「模块」，让依赖关系显式化。类加载仍按委派走，但「谁允许看见谁」由模块描述符决定。

模块描述符
module-info.java → module-info.class
声明模块名、requires（依赖）、exports（导出包）、opens（开放反射）、provides/uses（服务）。编译期与运行期都会校验。
模块解析与图
java.lang.module.ModuleLayer · Configuration
启动时解析根模块，沿 requires 构建模块图（依赖环检测）；ModuleLayer 分层承载不同来源的模块集合（如容器再叠加一层）。
模块与类加载器映射
Launcher：Bootstrap → 平台模块 → 应用模块
java.base 等基础模块 → Bootstrap；非基础平台模块 → Platform；应用/classpath 模块 → App。模块为类加载器提供命名空间边界。
未命名模块
classpath 上的类 · 自动模块
仍在 classpath 跑的代码属于未命名模块（读所有模块、不导出）；JAR 放进 module path 变成自动模块（名字取自文件名）——迁移的两条通道。
反射与 opens
--add-opens · java.lang.reflect
模块封装后，跨模块反射访问非 public/非 opens 成员报 InaccessibleObjectException；框架层常需 --add-opens 放行（Spring/Netty 的经典启动参数）。
06 类加载异常与排查 EXCEPTIONS & TROUBLESHOOTING

一句话理解：类加载的报错几乎都能用「谁在哪个阶段、少了什么」来对号入座。先分「编译期在不在」与「运行期找不找得到」两类。

异常 阶段 触发场景 关键区别 排查方向
ClassNotFoundException 加载 运行时按名字找类（反射、Class.forName、框架 SPI）但加载器找不到 受检异常，类「不存在的运行期报告」 看哪个加载器在找、classpath/module path 是否含该类
NoClassDefFoundError 加载 编译期存在、运行期缺失，或依赖类初始化失败被连带标记 Error，通常是「类在但加载失败」的连锁反应 -verbose:class 看加载到哪一步断掉，查依赖链
ExceptionInInitializerError 初始化 <clinit>（静态块/静态字段赋值）抛出异常 根因在 cause 里，常是静态代码写错 读 cause 定位静态初始化代码
VerifyError / ClassFormatError 验证 字节码非法、魔数/版本不符、被篡改或字节码增强出错 「文件本身有问题」 javap 检查字节码，核对 JDK 版本兼容
UnsupportedClassVersionError 加载 class 编译版本高于当前 JVM 支持版本 「编译器 vs 运行器」版本错位 javap -v 看 major version，升 JDK 或降编译 target
OOM: Metaspace 全链 动态生成类/热部署加载器泄漏，类元数据撑满元空间 「类太多」而非实例太多 jcmd GC.class_stats 看类占用，查加载器生命周期
07 验证实验：亲手观察类加载 VERIFY WITH TOOLS

一句话理解：类加载是「看不到的流程」，但 -verbose:class 能把它变成一行行日志。下面的命令与代码可以直接在本地 JDK 21 上跑。

-verbose:class · 观察加载序列
java -verbose:class HelloWorld
启动即打印数千行 [Loaded xxx from ...]。先看 java.base 全被 Bootstrap 加载，再看自己写的类由 App 加载——双亲委派的实证。
jcmd · 类层级与统计
jcmd <pid> VM.class_hierarchy java.lang.String
jcmd <pid> VM.classloader_stats
class_hierarchy 看继承树；classloader_stats 看每个加载器加载了多少类、占用多少元空间——Metaspace 排查的第一步。
javap · 读常量池
javap -v HelloWorld.class
反汇编看 CONSTANT_* 表项：全限定名、方法描述符、字符串字面量——「符号引用长什么样」的直观答案。
自定义加载器 · 打印加载过程
class MyLoader extends ClassLoader {
  protected Class<?> findClass(String name) {
    System.out.println("findClass: " + name);
    byte[] b = Files.readAllBytes(Path.of(name + ".class"));
    return defineClass(name, b, 0, b.length);
  }
}
覆写 findClass 并打印：先看到父加载器没找到才轮到它——模板方法模式的直观演示。
SPI 观察 · TCCL 是谁
System.out.println(
  Thread.currentThread()
       .getContextClassLoader());
打印 TCCL，通常是 AppClassLoader；再配合 ServiceLoader 加载 JDBC 驱动，体会「父问子要」的落地。
制造现场 · 触发类加载异常
java -cp . NoClassDefFoundDemo
java -XX:MaxMetaspaceSize=32m MetaGenDemo
删掉一个依赖类看 NoClassDefFoundError；用循环生成代理类（CGLIB）撑爆 32m 元空间，走一遍 Metaspace OOM 排查流程。

从「看得见」到「读源码」：先用工具把加载过程变成日志，再钻进 JDK 源码理解模板方法，最后用反例巩固委派模型。
