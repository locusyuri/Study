GraalVM
JVM 生态的高性能多语言运行时

简单说：GraalVM 是一套「给 JVM 换装升级」的发行版——用 Java 写的编译器替代 C2，支持提前编译成原生可执行文件，还能在同一个进程里跑 JS / Python / Ruby 等多种语言。

01 GraalVM 是什么 WHAT IS GRAALVM

一句话理解：GraalVM = OpenJDK（HotSpot 运行时 + 分代 GC）+ Graal 编译器 + Truffle 多语言框架，打包成一个可替换 `java` 的高性能发行版。

发行版定位
基于 OpenJDK · 兼容 java/javac 命令
它首先是「一个 JDK」：类库、运行时数据区、类加载、GC 都来自 HotSpot。差别在编译器与额外工具链，向下兼容现有 Java 代码。
三大件
Graal 编译器 · Truffle · Substrate VM
Graal 编译器（Java 写的 JIT）、Truffle（多语言实现框架）、Substrate VM（AOT 运行时）——三件事对应三种交付形态。
发行版家族
CE / EE / Mandrel
CE 社区版免费开源；EE 企业版多 AArch64 优化与编译器特性；Mandrel 是 Red Hat 面向 Quarkus 的 Native Image 发行版。
与 HotSpot 的关系
换编译器，不换运行时
JVM 模式 = HotSpot + Graal 编译器替换 C2；GC（G1/ZGC）与执行引擎其余部分仍是 HotSpot 的——执行引擎专题的 JIT 管道在此升级。
版本节奏
跟随 OpenJDK LTS · 如 for JDK 21 / 25
GraalVM 随 OpenJDK 的 LTS 版本出对应发行版（GraalVM for JDK 25 等）；主线代码仍开源在 github.com/oracle/graal。
解决什么痛点
启动慢 · 内存高 · 预热期
Serverless/微服务/CLI 工具/容器镜像：JVM 模式常因启动与常驻内存吃亏，Native Image 正是为这些场景而生。
02 Graal 编译器 THE GRAAL COMPILER

一句话理解：Graal 是一个用 Java 写的高级 JIT 编译器——同样的字节码，它能做比 C2 更深、更易扩展的优化，还能编译自己（自举）。

为什么用 Java 写编译器
compiler/ · 可读性 & 可扩展性
C2 是 C++ 写的老牌编译器，改动风险高；Graal 用 Java 写，优化 pass 是普通方法调用，能借 IDE 调试、能加新优化而不动 C2。
部分逃逸分析 PEA
比 C2 更强的标量替换
对象若只有部分字段逃逸，也能拆开优化——条件分支里才逃逸的对象，未逃逸路径照样标量替换，是 Graal 的招牌优化之一。
推测优化与逆优化
Speculation · Deoptimization
按「最常见的假设」激进优化（如类型未变），运行时假设被打破就逆优化回解释器重来——用栈上替换（OSR）衔接，保证正确性。
自举
用 Graal 编译 Graal
Graal 编译器自身跑在 Graal 编译的机器码上（自举），形成正向循环：编译器越优化，编译自己的速度越快。
进入 OpenJDK 主线
JDK 16 起 jdk.internal.vm.compiler
Graal 编译器已作为独立模块并入 OpenJDK，任何 JDK 都能用它实验性替代 C2——与「GraalVM 发行版」解耦。
观测方式
-XX:+UnlockExperimentalVMOptions -XX:Compiler=graal
普通 JDK 21 上即可开启 Graal JIT 实验开关；GraalVM 发行版默认使用。配合 -XX:+PrintCompilation 看编译事件。

专题图：JIT 与 AOT——同一条流水线的两个出口

左侧 JIT：运行中按热点逐层编译，可动态窥探（profiling）后深度优化；右侧 AOT：构建时一次性完成静态分析与编译，运行时不再有编译与预热。

03 Native Image 与 AOT NATIVE IMAGE & AOT

一句话理解：`native-image` 在构建时用「封闭世界分析」把应用整体编译成原生可执行文件——没有 JVM、没有预热，换来毫秒级启动与极小内存，代价是放弃运行时动态性。

构建流程
native-image 命令 · 构建期静态分析
分析可达代码 → 编译到机器码 → 打包成可执行文件（含自带的简化运行时 Substrate VM）。构建慢，运行快。
封闭世界假设
Closed World · 禁止动态加载类
Class.forName、动态代理、反射调用都必须「在构建期就可见」。凡是运行期才决定的类，AOT 根本不知道它存在。
反射与元数据配置
reflect-config.json · reachability-metadata
反射、代理、资源、JNI 都要在构建期通过 JSON 配置「预先声明」；GraalVM 提供 agent（-agentlib:native-image-agent）自动收集。
Substrate VM
substratevm/ · 为 AOT 写的运行时
一套独立的小型运行时：自带 GC（分代/Shenandoah 式）、线程与异常机制，不含 JIT。这就是「没有 JVM 也能跑」的秘密。
典型场景
Serverless · CLI · 微服务 · 容器
启动 50ms 级、镜像几十 MB、常驻内存低——Quarkus/Spring Native/Helidon 都围绕它做「云原生 Java」。
不适合的场景
重度反射框架 · 动态类 · 长生命周期热路径
Spring 全注解反射要大量配置；运行几小时的大服务，JIT 的峰值吞吐通常仍高于 AOT——它换掉的正是 JVM 的「自适应」。
维度 JVM 模式（HotSpot + Graal JIT） Native Image（AOT） 一句话结论
启动时间 秒级（类加载 + JIT 预热） 毫秒级（直接执行机器码） AOT 快 1~2 个数量级
常驻内存 JVM 自身开销 + 元空间 仅应用数据，无 JVM 层 AOT 显著更低
峰值吞吐 JIT 持续自适应优化 静态编译，无运行期优化 长跑大负载 JVM 更优
反射 / 动态代理 原生支持 需构建期 JSON 配置 JVM 省心
动态类加载 支持（Class.forName 等） 不支持（封闭世界） AOT 硬约束
GC 选择 G1 / ZGC 等全家桶 Substrate VM 自带（分代等） JVM 选择更多
构建产物 平台无关 .class + JVM 平台相关可执行文件 AOT 要按平台构建

专题图：Native Image 构建流水线（build-time vs run-time）

橙色 = 构建期，绿色 = 运行期。静态分析决定了「运行期不再有任何发现」；agent 收集的反射配置是连通两者的关键输入。

04 Truffle 与多语言 TRUFFLE & POLYGLOT

一句话理解：Truffle 是「用框架写语言解释器」的框架，所有语言编译到同一套中间表示，共享同一个 Graal JIT——于是 JS 和 Java 能在同一进程里互相调用。

语言实现框架
truffle/ · 自顶向下解释器
每种语言只需写一个 AST 解释器（自顶向下），Truffle 自动完成 specialization 与「部分求值」，再交给 Graal 编译成机器码。
Polyglot API
org.graalvm.polyglot · 一个进程互调
Java 里 new Context().eval("js", ...) 跑 JS，JS 里再调 Python 函数——共享堆与调用栈，无进程间序列化开销。
语言全家桶
JS/Node · Python · Ruby · R · Wasm · LLVM
GraalJS、GraalPython、TruffleRuby 等皆基于 Truffle；Sulong 跑 LLVM bitcode（C/C++/Rust），GraalWasm 跑 WebAssembly。
与 JVM 的关系
多语言代码共享 Graal 编译通道
各语言 AST 最终都进入 Graal IR——与 Java 字节码同一条优化/编译流水线，这是「多语言高性能」的技术底座。
Truffle 的代价
解释器预热 · 语言生态完整度
多语言进程启动更重、各语言库生态不如原生实现完整；适合「JVM 为主、少量脚本穿插」的场景，而非全量替换 Node/Python。
GraalPy 与 Python 生态
官方发行版内置 · 与 NumPy 兼容层
GraalPy 追求与 CPython 生态兼容（科学计算栈），并可在 JVM 内互调 Java——数据科学里 Java 调 Python 库的桥。

专题图：Polyglot 互调——所有语言通向同一条编译流水线

各语言解释器（AST）通过 Truffle 框架统一进入 Graal IR，再共享 Graal JIT 编译；Polyglot Context 是进程内互调的入口。

05 演进时间轴 TIMELINE

一句话理解：从 Oracle Labs 的科研项目，到 OpenJDK 官方模块——GraalVM 用了十几年走完「论文 → 发行版 → 标准」的路线。

GraalVM 关键节点

注意 2020 年前后两条线的交汇：Native Image 转正 + Graal 编译器并入 OpenJDK 主线，此后「GraalVM 发行版」与「任何 JDK 可用 Graal JIT」并行。

2011–2017
科研项目期 Oracle Labs 的 Graal 编译器（Java 写的 JIT）与 Truffle 语言框架论文相继发表；Maxine VM 与 Substrate VM 提供 AOT 验证平台。
2018
GraalVM 1.0 GA 首个正式发行版：基于 JDK 8/11，主打「多语言 + 高性能」，提供 CE/EE 两个版本与 gu 组件管理器。
2020
Native Image 转正 + 并入 OpenJDK 20.3 起 Native Image 正式 GA；同年 Graal 编译器作为 jdk.internal.vm.compiler 并入 OpenJDK 主线，任何 JDK 可实验启用。
2021–2023
云原生 Java 落地 Quarkus 默认 Mandrel、Spring Boot 3 原生支持、Micronaut/Helidon 跟进；GraalVM for JDK 17/21 按 LTS 节奏发布。
2025
GraalVM for JDK 25 跟随 JDK 25 LTS：Native Image 与分代 ZGC 协作、构建性能持续优化、GraalPy 生态扩展；gu 已退役，组件独立下载。
06 动手实验 VERIFY WITH TOOLS

一句话理解：同一个 HelloWorld，分别用 `java` 与原生可执行文件跑，用 `time` 量启动差距——再把 JIT 换成 Graal 对比编译日志，三件事就理解了大半。

确认版本 · 装的是 GraalVM
java -version
# openjdk version "25" 2025-09-16
# GraalVM CE 25.0.0 (build 25+36-jvmci-25.0)
输出带 GraalVM/JVMCI 字样即发行版；普通 JDK 也能装 Graal 编译器组件实验 JIT，但 native-image 工具链只在 GraalVM/Mandrel。
安装工具链 · native-image
# GraalVM 20.x 及以前：gu install native-image
# 21+：随发行版独立下载 Native Image 组件包
native-image --version
gu 已在现代版本退役，组件改为独立下载安装；Windows 上首次构建需要 Visual Studio 的 C 工具链（cl.exe）。
第一个 AOT · HelloWorld
javac Hello.java
native-image Hello -o hello
# 构建 30s~1min（含静态分析）
.\hello.exe
构建期做封闭世界分析较慢，运行期毫秒即出。对比：java Hello 的启动通常要几百毫秒到秒级。
普通 JDK 开 Graal JIT
java -XX:+UnlockExperimentalVMOptions \
     -XX:Compiler=graal -XX:+PrintCompilation \
     -version
JDK 16+ 内置 Graal 编译器模块；PrintCompilation 输出里能看到编译器名（graal 而非 C2）与编译层级。
Polyglot 互调 · Java 调 JS
import org.graalvm.polyglot.*;
var ctx = Context.create();
Value fn = ctx.eval("js",
  "x => x * 2 + 1");
System.out.println(fn.execute(21)); // 43
同一进程内跑 JS 并取回结果；还可 js→python、python→Java 双向互调，体验「多语言共享堆」。
反射自动配置 · agent
java -agentlib:native-image-agent=config-output-dir=./META-INF/native-image Hello
native-image Hello -o hello
跑一遍带 agent 的 JVM 版，自动生成 reflect-config.json / proxy-config.json；构建时自动读取 META-INF/native-image 下的配置。
07 源码学习路线 SOURCE CODE MAP

一句话理解：GraalVM 主线仓库 oracle/graal 按模块分目录，学编译器进 `compiler/`、学 AOT 进 `substratevm/`、学多语言进 `truffle/`——比 OpenJDK 仓库小得多，sparse checkout 即可。

仓库规模
github.com/oracle/graal · 数百 MB 级
比 OpenJDK 全量仓库小；若只学一个模块，用 git sparse-checkout 只拉 compiler/ 或 substratevm/，本机磁盘与克隆时间都省。
compiler/ 入口
GraalCompiler.java · 编译主流程
看 HighTier/MidTier/LowTier 分层优化、PhiNode 数据流、escape analysis；对照 execution-engine.html 的 JIT 管道概念。
substratevm/ 入口
NativeImageGenerator.java · 静态分析
封闭世界分析（Points-to analysis）→ 图构建 → 编译 → 镜像写入；配套看 SVM 自带 GC（NImageHeap/分代）的实现。
truffle/ 入口
TruffleLanguage.java · 语言 SPI
看懂「写解释器 + 部分求值」的接口抽象，再挑 GraalJS/GraalPy 一个具体实现跟进 Node/AST 的执行与 specialization。
JVMCI 桥
jdk.internal.vm.compiler · JVM Compiler Interface
Graal 之所以能替换 C2，靠 JVMCI 这套 HotSpot 编译接口：Graal 通过它拿到字节码、回填机器码，是「换编译器不换运行时」的接线层。
学习顺序建议
先 JVM 基础 → 再 Graal JIT → 后 AOT/Truffle
没有执行引擎/GC 基础直接读 Graal 会淹没在 IR 细节里；本仓库 wiki/JVM 的 execution-engine 与 garbage-collection 就是前置课。
建议阅读路径

从「JVM 背景」到「GraalVM 三条支线」：先看懂它与 JVM 的异同，再分别走 JIT / AOT / 多语言，最后决定要不要 sparse checkout 源码。

1
补 JVM 前置

回 execution-engine.html 看 C2 与分层编译、garbage-collection.html 看 GC——Graal 只是「换编译器」，底子没变。

2
分清三个身份

GraalVM = 发行版 / Graal = JIT 编译器 / Native Image = AOT 工具链；别把「发行版」与「编译器」混为一谈。

3
跑通 JIT 实验

普通 JDK 上 -XX:Compiler=graal 开启并 PrintCompilation 对比；再体验 PEA 与逆优化的日志行为。

4
做一次 Native Image

HelloWorld → agent 收集反射配置 → 带框架（如 Quarkus 模板）构建；用 time 量化启动与内存差异。

5
试 Truffle 互调

Polyglot Context 里 Java↔JS↔Python 传值回调，理解「多语言共享一条编译流水线」。

6
决定是否深挖源码

回 OVERVIEW.html 看整个 JVM 体系；若真学编译器，sparse checkout oracle/graal 的 compiler/ 或 substratevm/ 再开读。
