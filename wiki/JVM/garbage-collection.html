垃圾回收
JVM 内存的自动管家

简单说：GC 从「根」出发做可达性分析，不可达的对象就是垃圾；再用合适的算法腾出空间。收集器的进化史，就是「尽量少停顿、少浪费」的历史。

01 可达性判定 REACHABILITY ANALYSIS

一句话理解：「是不是垃圾」不看引用计数，而看「从根出发能不能走到」。走得到的是活对象，走不到的就是垃圾——这天然解决了循环引用问题。

GC Roots 集合
栈帧局部变量 · 静态字段 · JNI 引用
正在执行的方法里的引用、类的静态字段、JNI 全局/局部引用、运行时常量池引用、同步监视器、JVM 内部引用（System Class 等）。
为什么不用引用计数
循环引用：A↔B 彼此计数为 1 却无人可达
引用计数需每次赋值维护计数、无法处理循环引用、还有额外空间开销；可达性分析从根遍历，循环引用自然判死。Python 用计数+额外机制，JVM 直接选可达性。
强引用
Object obj = new Object()
默认引用类型：可达即存活，GC 绝不回收。内存泄漏的本质，就是「本该死的对象被强引用链拴着」。
软 / 弱 / 虚引用
java.lang.ref.Soft/Weak/PhantomReference
软引用：内存不足才回收（缓存场景）；弱引用：下次 GC 即回收（ThreadLocal 的 key）；虚引用：拿不到对象仅收通知（DirectByteBuffer 清理）。都配 ReferenceQueue。
finalize 与 Cleaner
java.lang.Object.finalize · java.lang.ref.Cleaner
finalize 已废弃（JDK 9 起 @Deprecated，执行时机不可控）；Cleaner 基于 PhantomReference 做确定性清理，是资源释放的现代姿势。
三色标记
并发标记的核心抽象
白=未访问、灰=正在访问、黑=访问完成。并发标记最怕「灰→白」漏标；SATB 快照与写屏障就是为堵这个洞（G1 章节详述）。

专题图：从 GC Roots 出发的引用图

实线 = 可达引用，虚线圆 = 不可达（垃圾）。注意 E 虽然被 D 引用，但 D 自身不可达，E 也随之下沉为垃圾——循环引用同理判死。

02 三大回收算法 COLLECTION ALGORITHMS

一句话理解：三种算法各有取舍：要么有碎片、要么浪费空间、要么搬对象。没有银弹，所以按「新生代死得快、老年代活得久」分而治之。

算法 怎么做 优点 缺点 用在哪
标记-清除
Mark-Sweep		 从根标记存活对象，再统一清除未标记对象 实现简单，不移动对象 内存碎片化；标记与清除两次遍历 CMS（历史）、G1 的部分阶段
复制
Copying		 把存活对象复制到另一半空间，原空间整体废弃 无碎片、分配只需移动指针 浪费一半空间（存活率低时划算） 新生代 Eden → S0/S1（默认 8:1:1）
标记-整理
Mark-Compact		 标记存活对象后向一端移动，清理边界外空间 无碎片、空间利用率高 移动对象需更新引用，停顿长 老年代（Parallel 等分代收集器）
分代假设
弱代假设 · 大部分对象朝生夕灭
绝大多数对象很快变垃圾（局部变量）→ 新生代用复制算法最划算；少数活下来的进老年代 → 用标记-整理减少碎片。分治的核心依据。
分配与指针
TLAB · bump-the-pointer
Eden 是连续空间，分配 = 指针后移（bump），比空闲列表快；每线程 TLAB 预分配一块，连 CAS 都省了。GC 停顿与分配速度强相关。
碎片化代价
碎片 → 大对象分配失败 → 提前 Full GC
标记-清除留下的碎片会导致「空间够但放不下连续大对象」，触发不必要的 Full GC——这是 CMS 退场的核心原因之一。
03 分代回收与收集器演进 GENERATIONAL GC & COLLECTORS

一句话理解：收集器 = 算法 × 线程模型 × 停顿策略的封装。从 Serial 到 ZGC，主线始终是「把 STW 尽量变短、把并发做进去」。

Minor / Major / Full GC
新生代 / 老年代 / 整堆
Minor GC 只回收新生代（复制算法，很快）；Major/Full GC 处理老年代（标记-整理或并发），停顿通常大。目标是「Full GC 越少越好」。
Parallel 收集器
-XX:+UseParallelGC · JDK 8 默认
多线程并行回收，吞吐优先（-XX:GCTimeRatio），适合批处理/离线任务；吞吐 = 用户代码时间 / (用户代码 + GC 时间)。
CMS 的教训
-XX:+UseConcMarkSweepGC · JDK 9 起废弃 · JDK 14 移除
首个主打低停顿的并发收集器，但并发标记占用 CPU、无法处理浮动垃圾、碎片化严重——「低延迟方向是对的，实现撑不住」，被 G1 接棒。
Shenandoah
gc/shenandoah/ · 连接缓冲 + 转发指针
与 ZGC 同时代的低延迟收集器：并发搬运对象，用 Brooks 指针 + 读屏障；已进入 OpenJDK 主线，与 ZGC 是「两条技术路线」的对照。

演进时间轴：从 Serial 到 ZGC

每一代解决上一代的痛点：单线程 → 多线程 → 并发 → Region 化 → 染色指针。停顿目标从「尽量短」走向「确定毫秒级」。

JDK 1.0
Serial 串行收集器 单线程回收，回收时全线 STW。桌面时代够用；今天主要用于客户端模式与 JVM 自身引导。
JDK 5
Parallel 并行收集器 多线程并行回收，吞吐优先；JDK 8 的默认收集器，批处理/离线场景至今常用。-XX:+UseParallelGC。
JDK 7
CMS 并发标记-清除 首次「并发回收」：标记与清理与用户线程并行，大幅缩短停顿；但碎片与 CPU 抢占问题严重，JDK 9 标记废弃。
JDK 9
G1 成为默认 Region 化堆 + RSet + SATB，停顿可预测（-XX:MaxGCPauseMillis）；把「物理连续」的假设彻底打破，为后续收集器铺路。
JDK 15+
ZGC / Shenandoah 成熟 ZGC 染色指针 + 读屏障，停顿不随堆大小增长（毫秒级）；Shenandoah 并发搬移对象。JDK 21 的 ZGC 已支持分代。
04 G1 收集器 GARBAGE-FIRST

一句话理解：G1 把堆切成 Region，每次挑「垃圾最多」的 Region 回收（Garbage-First 的由来），用「回收收益排序」把停顿控制在目标之内。

Region 布局
gc/g1/ · -XX:G1HeapRegionSize
堆切成约 2048 个 Region（1~32MB），Eden/Survivor/Old/Humongous 都是 Region 的「角色」；大对象占连续多个 Humongous Region。
RSet 记忆集
gc/g1/g1RemSet.cpp · 卡表 Card Table
记录「谁引用了我」：回收一个 Region 时不必全堆扫描，只查 RSet 找跨区引用。写屏障维护卡表脏位，是空间换时间的核心。
并发标记与 SATB
g1ConcurrentMark.cpp · 三色标记
SATB（Snapshot-At-The-Beginning）快照：并发标记开始时拍引用快照，用写屏障记录增量，保证不漏标——白对象只要在快照里可达就安全。
混合回收
G1 的回收循环：Young → 并发标记 → Mixed
先只收年轻代（Eden+Survivor），IHOP 触发并发标记，标记后进入 Mixed 阶段按收益挑老年代 Region 回收；大停顿由「增量回收」摊薄。
停顿预测模型
-XX:MaxGCPauseMillis=200 · 默认
用历史回收速率推算「这次能收几个 Region」，动态调整年轻代大小满足停顿目标——G1 的停顿是「软目标」，突发大对象/大 Region 仍可能超。
G1 的代价
RSet 内存开销 · 写屏障成本 · 并发标记 CPU
Region 化 + 记忆集让单次停顿短，但维护 RSet/屏障有额外开销；吞吐通常略低于 Parallel——用一点吞吐换延迟，是 G1 的定价。
05 ZGC 与低延迟收集器 ZGC & LOW-PAUSE GC

一句话理解：ZGC 的目标是「停顿不随堆变大」——10G 堆和 100G 堆都只停毫秒级，靠染色指针和读屏障把回收搬进并发阶段。

染色指针
gc/z/zPointer.hpp · 指针高 4 位存状态
64 位指针用 4 位标记：Finalizable/Remapped/Marked0/Marked1。对象「搬没搬、标记没标记」都编码在指针里，读指针即可知状态。
读屏障
gc/z/zBarrier.cpp
读对象引用时检查指针状态：若已标记搬移，就地修正指针（自愈）。让「用户线程看到的一直是新地址」，回收完全并发进行。
分代 ZGC
JDK 21 · 年轻代/老年代 ZGC
加入分代后：年轻代回收更频繁但更便宜，老年代回收频率大幅下降——吞吐与延迟双优，大堆场景的现代默认选择之一。
适用场景
-XX:+UseZGC · 大堆 · 低延迟服务
推荐堆 ≥ 8G 使用（小堆收益不明显）；牺牲一些吞吐与内存（染色指针/屏障开销），换「GC 不再出现在 P99 里」。
Shenandoah 对照
gc/shenandoah/ · 转发指针 + 连接缓冲
不用染色指针，用对象内嵌转发指针 + 读屏障；两者思路互补：ZGC 状态在指针里，Shenandoah 状态在对象里。
06 GC 调优 GC TUNING

一句话理解：调优不是堆参数，是「定目标 → 看日志 → 找病根 → 最小改动」。先分清楚是「堆太小」还是「对象该回收没回收」还是「晋升太快」。

三角权衡
吞吐 / 延迟 / 内存占用
三选二：要吞吐给大堆少 GC（Parallel）、要延迟选 G1/ZGC、要省内存就得接受更频繁的回收。先定业务目标再选收集器。
关键参数
-Xms/-Xmx · -XX:MaxGCPauseMillis · -XX:NewRatio
堆大小建议相等且留 30% 余量；停顿目标给 G1 定软目标；NewRatio 控制新生代/老年代比例。改一个参数，看一组日志。
GC 日志解读
-Xlog:gc*:file=gc.log · JDK 9+ 统一
看三类信号：GC 频率（太频繁→堆小/分配快）、停顿时长（太长→老年代回收/大对象）、晋升速率（太快→对象过大/阈值低）。
常见病根
频繁 Full GC · 过早晋升 · 大对象 · 内存泄漏
Full GC 频繁先怀疑泄漏或堆小（转储确认）；过早晋升看 Survivor 是否装不下；大对象（Humongous）看分配路径；泄漏用 MAT 找引用链。
过早晋升
-XX:MaxTenuringThreshold · -XX:TargetSurvivorRatio
Survivor 装不下存活对象时提前晋升老年代；调大 Survivor（-XX:SurvivorRatio）或降阈值能缓解，但根因常是「生成了太多长生命周期对象」。
调优流程
测量 → 假设 → 验证（一次只改一个）
先用 JFR/jstat 采集基线 → 提出假设（如「Survivor 太小导致晋升」）→ 改一个参数 → 同负载复测对比 → 记录结论。不猜、不堆参数。
07 验证实验：亲手看 GC VERIFY WITH TOOLS

一句话理解：造一个「活着不死的对象」，用 GC 日志亲眼看它从 Eden 一路走到老年代。看懂一次晋升，就理解了整个分代模型。

-Xlog:gc · 开启 GC 日志
java -Xlog:gc*:file=gc.log:time,uptime \
     -Xmx256m GcDemo
记录每次 GC 的类型（Young/Full）、前后用量、停顿时长。调优的第一工具，先看频率再看时长。
jstat · 实时各代用量
jstat -gc <pid> 1000
每秒采样 EU/OU（Eden/Old 用量）、YGC/FGC 次数与耗时。观察「Eden 涨 → Young GC → 存活进 S → 逐步升 OU」。
JFR · GC 事件时间线
java -XX:StartFlightRecording=duration=60s,\
filename=gc.jfr GcDemo
用 JMC 打开，看 GC 事件时间轴、堆使用曲线、分配压力（Allocation Profiling）——生产可开的低开销记录。
制造 Minor GC · 观察晋升
java -Xmx128m -Xlog:gc* AgeDemo
循环 new 短命对象 → 大量 Young GC；再让部分对象活得久 → 日志里出现 "promotion"；用 -XX:MaxTenuringThreshold=1/15 对比晋升速度。
制造 Full GC · 看停顿
java -Xmx64m -Xlog:gc* LeakDemo
用静态集合不断加对象 → 老年代打满 → Full GC 反复出现 → OOM。配 -XX:+HeapDumpOnOutOfMemoryError 转储，MAT 分析泄漏链。
切换收集器 · 对比停顿
java -XX:+UseParallelGC -Xlog:gc* GcDemo
java -XX:+UseG1GC      -Xlog:gc* GcDemo
java -XX:+UseZGC       -Xlog:gc* GcDemo
同一负载三套收集器，对比 Young/Full GC 次数与单次停顿：Parallel 吞吐高但停顿大，ZGC 停顿毫秒级但吞吐略低——三角权衡的实证。
