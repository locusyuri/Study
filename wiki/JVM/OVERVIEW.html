运行时、内存与执行引擎总览

简单说：.class 字节码进来（类加载）→ 在内存里跑（运行时数据区）→ 用完的对象被回收（垃圾回收）→ 代码被解释或编译执行（执行引擎）。本页把这套体系按七大领域组织，每个知识点都标注了 JDK 源码落点，便于对照阅读。

01 类加载机制 CLASS LOADING

一句话理解：.class 文件只是一个蓝图，JVM 按需把它读进内存、校验、准备好静态存储，最终生成可用的 Class 对象。主线是「类加载器层级 → 双亲委派 → 五阶段生命周期」。

类加载器层级
java.lang.ClassLoader · java.lang.module
Bootstrap（启动类加载器，加载 java.base）→ Platform（平台类加载器）→ App（应用类加载器）→ 自定义。JDK 9 模块化后由 Launcher 构造，层级由「父引用」串联。
双亲委派模型
ClassLoader.loadClass()
先问父加载器，父找不到才自己加载。保证核心类只被 Bootstrap 加载一次，避免同名类被替换、杜绝核心 API 被篡改。
五阶段生命周期
HotSpot: classfile/classFileParser.cpp
加载 Loading → 验证 Verification → 准备 Preparation → 解析 Resolution → 初始化 Initialization。前 4 步对应「读进来、验真伪、备空间、连符号」，第 5 步才执行静态代码。
常量池与符号引用
classfile/classFileParser.cpp · constantPool.cpp
类文件里的 CONSTANT_Class / Methodref 等是符号引用，解析阶段才把它们替换为直接引用（内存地址/偏移）。
打破双亲委派
java.util.ServiceLoader · SPI 机制
JDBC / JNDI 等 SPI 场景「父问子要」；Tomcat 等容器按应用隔离类加载器。理解双亲委派，才能理解这些反例为什么存在。
模块化 JPMS
java.lang.module.ModuleLayer
JDK 9 起模块描述符（module-info.class）参与解析：module → package → class，类加载与模块边界共同决定可见性。
相关异常与 OOM
java.lang.NoClassDefFoundError · OutOfMemoryError: Metaspace
类找不到、静态初始化失败、元空间放不下类元数据，是类加载层的三类典型故障出口。
02 运行时数据区 RUNTIME DATA AREAS

一句话理解：线程私有的是「干活用的草稿纸」，线程共享的是「放东西的大仓库」。栈管执行、堆管对象、方法区管类信息，这是内存模型的第一性原理。

程序计数器 PC
java.lang.Thread
线程私有，记录当前执行到哪条字节码。唯一不会 OOM 的区域；线程切换后靠它恢复执行位置。
虚拟机栈 JVM Stack
java.lang.StackOverflowError
线程私有，由栈帧组成：局部变量表 + 操作数栈 + 动态链接 + 返回地址。每个方法调用压一帧，递归过深抛 StackOverflowError。
本地方法栈
jdk.internal.misc.Unsafe
为 native 方法服务。HotSpot 中与虚拟机栈合并实现；Unsafe 是 Java 触碰本地内存/对象布局的窗口。
堆 Heap
java.lang.OutOfMemoryError: Java heap space
线程共享，几乎所有对象实例的出生地。分代收集下为 新生代(Eden+S0+S1)+老年代；G1 起按 Region 划分，不再物理连续。
方法区 / 元空间
java.lang.Class · OutOfMemoryError: Metaspace
JDK 8 起用本地内存的 Metaspace 承载：类元数据、运行时常量池、方法字节码。静态变量在 JDK 7 后移入堆，注意区分。
字符串常量池
java.lang.String · String.intern()
JDK 7 起移到堆中，存储字符串字面量与 intern 结果；是理解「== 与 equals」差异、以及常量池 OOM 的关键。
直接内存
java.nio.ByteBuffer · DirectByteBuffer
堆外内存，NIO 零拷贝与 Netty 的基础；不受 -Xmx 约束，由 -XX:MaxDirectMemorySize 限制，常见于「看着堆很小却 OOM」的排查。
03 对象模型与内存布局 OBJECT MODEL & MEMORY LAYOUT

一句话理解：new 出来的对象在堆里是一块有固定结构的二进制块：头（身份信息）+ 数据（字段值）+ 对齐（补位）。理解对象布局，才能理解锁、GC 年龄、内存占用。

对象头 Mark Word
HotSpot: oops/markWord.hpp
64 位里按位复用：锁状态、hashCode、GC 分代年龄、是否偏向。一个字段同时承载多个身份，是 JVM 极致的位压缩。
类型指针 Klass Pointer
oops/oopDesc.hpp · klass.hpp
指向方法区中的 Klass（类元数据），对象据此找到自己的类。开启压缩指针后从 8 字节压到 4 字节。
实例数据与对齐
oops/klass.hpp · java.lang.Object
字段按声明序/重排布局，8 字节对齐填充。字段顺序影响对象大小与缓存行，是 jol 工具能测出「重排省内存」的原因。
对象创建路径
jdk.internal.misc.Unsafe.allocateInstance
new 的完整链路：类加载检查 → 分配内存（指针碰撞/空闲列表）→ 零值初始化 → 设置对象头 → 执行 <init>。TLAB 线程本地分配避免竞争。
指针压缩
-XX:+UseCompressedOops（JDK 8 起 64 位默认开启）
堆 ≤32G 时普通对象指针用 32 位表示，省一半引用内存；堆超过 32G 自动关闭，是「为什么 32G 是个坎」的由来。
逃逸分析
HotSpot: c2/escapeAnalysis.cpp
对象不逃逸方法作用域 → 栈上分配或标量替换（拆成字段），配合锁消除。解释了「局部小对象为什么不产生 GC 压力」。
对象大小观测
jdk.jol（OpenJDK 官方工具，IDEA 插件可用）
Java Object Layout：打印对象头、字段偏移、占用字节。把「内存布局」从抽象概念变成一行行可核对的数据。
04 垃圾回收 GARBAGE COLLECTION

一句话理解：JVM 从「根」出发做可达性分析，不可达的对象就是垃圾，再用不同算法腾出空间。现代收集器的进化史 = 降低停顿时间（STW）的历史。

可达性分析
HotSpot: gc/shared/collectedHeap.cpp
GC Roots：栈帧局部变量、静态字段、JNI 引用、常量池引用、同步监视器、JVM 内部引用。从根出发遍历，不可达即垃圾。
引用类型体系
java.lang.ref.Reference · Soft/Weak/PhantomReference
强引用（默认）→ 软引用（内存不足才回收，缓存场景）→ 弱引用（下次 GC 即回收，ThreadLocal 键）→ 虚引用（无法访问对象，仅通知，DirectByteBuffer 清理用）。
三大基础算法
gc/shared/ · gc/g1/
标记-清除（碎片化）、复制（新生代，无碎片但浪费一半）、标记-整理（老年代，移动对象）。分代 = 三种算法的组合拳。
分代与晋升
gc/shared/generationSpec.hpp
新生代 Eden + 两个 Survivor（默认 8:1:1），Minor GC 存活对象在 S0/S1 间复制，年龄到阈值（默认 15）晋升老年代；大对象直接进老年代。
G1 收集器
gc/g1/ · -XX:+UseG1GC（JDK 9 起默认）
堆划分为 Region，逻辑分代、物理连续；RSet 记录跨区引用，并发标记 + 可预测停顿（-XX:MaxGCPauseMillis）。
ZGC / Shenandoah
gc/z/ · gc/shenandoah/
低延迟收集器：ZGC 用染色指针 + 读屏障，停顿不随堆大小增长（毫秒级）；Shenandoah 用连接缓冲 + 转发指针。JDK 21 中 ZGC 已支持分代。
并发标记与屏障
gc/g1/g1ConcurrentMark.cpp · cardTable.hpp
三色标记（白灰黑）防漏标，SATB 快照 + 写屏障处理并发引用变化；卡表 Card Table 记录跨代/跨区引用，是 Remembered Set 的底层。
05 执行引擎与字节码 EXECUTION ENGINE & BYTECODE

一句话理解：字节码是 JVM 的「汇编」，执行引擎先用解释器逐条翻译，热点代码再被 JIT 编译成机器码直接执行。性能的秘密全在「编译到什么程度」。

字节码指令集
javap -c 反汇编 · HotSpot: interpreter/bytecodeInterpreter.cpp
约 200+ 条指令，基于操作数栈：load/store、运算、new、invokevirtual/invokestatic、跳转。一条 Java 语句 = 若干条字节码。
解释执行
interpreter/ · templateTable.cpp
逐条取指-解码-执行，启动快但慢。HotSpot 用模板解释器：每个字节码指令预生成机器码模板。
分层编译
runtime/compilationPolicy.cpp · -XX:+TieredCompilation（默认）
C1（第 1~3 层）：快速编译 + 采集 profile；C2（第 4 层）：慢但激进优化。方法计数器和回边计数器判定热点，-XX:CompileThreshold 可调。
方法内联
c2/ · -XX:MaxInlineSize
JIT 最重要优化：把被调方法体直接展开到调用处，消除调用开销并让后续优化「看得更远」。getter/setter 几乎必被内联。
逃逸分析优化链
c2/escapeAnalysis.cpp
栈上分配、标量替换、锁消除、消除无用字段——都建立在「对象没逃逸」的证明上。C2 的看家本领。
动态调用 invokedynamic
java.lang.invoke.* · LambdaMetafactory
JDK 7 引入，Lambda、字符串拼接、序列化等全靠它：调用点先引导（bootstrap）解析策略，再按需绑定，为语言特性留出后门。
观测编译产物
-XX:+PrintCompilation · -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining
看哪些方法被编译、为何内联失败，是调优「为什么这么慢」的第一步。
06 并发与内存模型 JMM & CONCURRENCY

一句话理解：JMM 规定「线程什么时候能看到别人的写入」，锁与 volatile 是达成这个约定的工具。它不管理真实硬件缓存，而是定义一套抽象的可见性规则。

JMM 抽象
java.lang.Thread · 主内存/工作内存模型
每个线程有私有工作内存（寄存器/缓存抽象），变量读写在副本上进行，何时同步回主内存由 JMM 规则决定。对应真实硬件：CPU 缓存 + 缓存一致性。
happens-before
详见下方专题②
8 条规则（程序次序、锁、volatile、传递、线程 start/join、中断、final、对象构造）：A happens-before B 则 A 的写入对 B 可见。是判断并发正确性的「证明依据」。
volatile
jdk.internal.misc.Unsafe · 内存屏障
读屏障/写屏障禁止重排序 + 强制写回主内存。保证可见性与有序性，但不保证原子性（i++ 仍不安全）。经典用法：状态标志、双重检查锁。
synchronized 与锁升级
HotSpot: runtime/synchronizer.cpp · ObjectMonitor
Monitor 机制；锁状态：无锁 → 偏向 → 轻量级（CAS 自旋）→ 重量级（阻塞）。JDK 15 起偏向锁废弃，轻量级锁成为默认快路径。
AQS 框架
java.util.concurrent.locks.AbstractQueuedSynchronizer
CLH 队列 + state 状态机：ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 都是它的子类。理解 AQS = 理解半个 JUC。
并发容器与原子
java.util.concurrent.ConcurrentHashMap · java.util.concurrent.atomic.*
CHM 分段锁演进到 CAS + synchronized 细粒度锁；Atomic* 基于 Unsafe 的 CAS + volatile 字段，配合 LongAdder 应对高并发计数。
线程池
java.util.concurrent.ThreadPoolExecutor
核心线程 → 工作队列 → 最大线程 → 拒绝策略四段式；ctl 一个 int 打包 workerCount + runState。线程工厂、拒绝策略、队列选型是调优入口。
07 性能监控与调优 MONITORING & TUNING

一句话理解：先用工具拿到「内存、GC、线程、锁」四类现场数据，再反向定位到代码。调优不是调参数，是「测量 → 假设 → 验证」的循环。

JVM 命令行工具
jps · jstat · jinfo · jmap · jstack · jcmd（bin/ 下）
看进程、看 GC/类加载统计、看参数、堆转储、线程快照。jcmd 是 JDK 8 后的「瑞士军刀」，可替代大部分子命令。
JFR 与 Mission Control
jdk.jfr · jfr 命令 · JDK Flight Recorder
低开销的飞行记录器：GC、锁、IO、分配采样全覆盖，生产环境常开；配合 JMC 可视化分析事件时间线。
GC 日志
-Xlog:gc*:file=gc.log:time,uptime,level,tags（JDK 9 起统一）
统一日志框架 -Xlog 取代 PrintGCDetails。看 GC 频率、停顿、晋升速率，判断「内存该加还是该减」。
核心参数速查
-Xms/-Xmx · -XX:MetaspaceSize · -XX:MaxGCPauseMillis · -XX:+UseG1GC / +UseZGC
堆大小（建议相等避免扩容）、元空间、停顿目标、收集器选择。参数是手段，目标是吞吐/延迟/内存的三角权衡。
OOM 分类与排查
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=
Java heap space / Metaspace / Direct buffer memory / StackOverflowError / GC overhead limit：先看类型定区域，再用 MAT/jhat 分析堆转储定位泄漏。
线程与锁分析
jstack · jcmd Thread.print · 死锁检测
线程状态（RUNNABLE/BLOCKED/WAITING）+ 栈顶方法；jstack 自动检测死锁环。CPU 高时用 top -H + jstack 对线程 id 定位热点。
常用工具链
jol（对象布局）· MAT（堆分析）· async-profiler（火焰图）
三件套：jol 看内存布局、MAT 找泄漏、async-profiler 出 CPU/分配火焰图。IDE 插件（IDEA 自带 profiling）可覆盖大部分场景。
专题精讲

把跨领域的知识点串成完整链路：一个对象的一生、happens-before 八大规则、类加载五阶段详解。这是理解「内存」与「并发」的钥匙。

① 一个对象的一生LIFE CYCLE

  • 1 · 类加载：首次 new 触发类加载五阶段，类元数据进入方法区
  • 2 · 分配：TLAB 优先，失败走 CAS；Eden 放不下则直接进老年代
  • 3 · 初始化：零值 → 对象头（锁/年龄/hash）→ <init> 执行构造
  • 4 · 使用：栈帧局部变量表持有引用，可能逃逸也可能被内联优化
  • 5 · 可达性变化：引用置空/出栈后不可达，进入垃圾候选
  • 6 · 回收：Minor GC 幸存者复制 → 晋升老年代 → Full GC 标记整理
  • 7 · finalize 与终结：finalize 机制已废弃（JDK 9 起），Cleaner 取而代之

② happens-before 八大规则JMM

1 程序次序 同线程内，写在前 → 读在后 2 监视器锁 解锁 → 后续加锁 3 volatile 写 volatile → 之后读同一 volatile 4 传递性 A → B 且 B → C，则 A → C 5 线程启动 Thread.start() → 该线程内所有动作 6 线程终止 线程内动作 → 其他线程 join() 返回后 7 线程中断 interrupt() → 检测到中断（isInterrupted） 8 对象终结 构造完成 → finalize() 开始

③ 类加载五阶段详解CLASS LIFE CYCLE

  • 加载 · 读字节流 → 解析为方法区数据结构 → 生成 java.lang.Class
  • 验证 · 文件格式/元数据/字节码/符号引用四关，防恶意字节码
  • 准备 · 为静态字段分配内存并赋「零值」（不是代码里的初值）
  • 解析 · 符号引用 → 直接引用；可延迟到首次使用（lazy）
  • 初始化 · 执行 <clinit>：静态块与静态字段赋值；唯一被主动使用触发的阶段
  • 触发点：new / getstatic / putstatic / invokestatic / 反射 / 初始化子类
建议阅读路径

按依赖顺序组织：先「内存长什么样」（数据区+对象），再「东西怎么进来怎么出去」（类加载+GC），再「代码怎么跑」（执行引擎），最后「多线程怎么协作」与「怎么观测」。JDK 标准库类可直接在 IDE 里看 src.zip，HotSpot 路径供在线浏览。
