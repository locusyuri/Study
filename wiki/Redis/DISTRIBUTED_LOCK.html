Redis 分布式锁全解

分布式锁的本质：让"多个进程/实例"在共享临界区上达成互斥。Redis 用一条原子命令 SET key value NX PX ttl 就能实现，但"能加锁"与"锁可靠"之间，隔着过期时间、误删、主从切换、时钟跳跃等一连串坑 —— 本页从源码逐层拆解。

01 为什么需要分布式锁 WHY A DISTRIBUTED LOCK

单机内我们用互斥量/信号量解决线程互斥；一旦服务拆成多个进程、多台机器，锁就必须放在"大家都能访问的共享存储"上 —— 数据库、ZooKeeper、Redis 都是候选，Redis 因为内存原子命令成为最轻量的选择。

方案互斥载体取舍
单机锁线程 / 进程内最快，但只在单机内有效，跨进程/跨机器失效
数据库锁唯一索引 / SELECT FOR UPDATE可靠但慢，DB 是瓶颈；锁释放依赖事务
ZooKeeper 锁临时顺序节点强一致、无超时误删问题，但多一次协调依赖、运维重
Redis 锁 轻量SET NX 原子命令微秒级、实现简单；可靠性依赖部署方式（单点/主从/多节点）
  • 核心矛盾：分布式环境下没有"全局唯一线程"，必须借助一个所有参与者都能访问的协调者；锁的正确性 = 协调者的原子性 + 客户端对边界条件的处理。
  • Redis 的天然优势：单线程事件循环（ae.c）让"检查 + 写入"天然原子，这是后面所有方案的地基。
02 从 SETNX 到原子 SET：一条命令的演进史 HISTORY

分布式锁的"标准姿势"不是一天形成的：SETNX + EXPIRE 两步走有死锁隐患，2.6.12 起 SET NX EX 一步原子化，之后 Lua 脚本与 8.x 原生条件命令继续补齐能力。

1.x远古
SETNX + EXPIRE 两步走 非原子
先 SETNX 后 EXPIRE：若第一步后进程崩溃，key 永不消失 —— 死锁。单线程模型保证每条命令原子，但"两条命令之间"不是。
2.6.12里程碑
SET key value NX EX ttl 一步原子 标准
setGenericCommand（t_string.c:87）在单次命令内完成"不存在才写 + 附带过期"，天然原子 —— 官方文档自此推荐这一姿势。
3.2脚本
EVAL Lua：解锁校验原子化
evalCommand（eval.c:633）让"比较 value + DEL"变成一条原子脚本，解决误删问题（详见 04）。
2015算法
RedLock 算法发布
antirez 提出多节点多数派加锁，应对单点/主从切换丢锁；随后引发与 Martin Kleppmann 的著名论战（详见 06）。
8.x原生 CAS
SET IFEQ / DEL IFEQ 条件命令
SET key value IFEQ old（t_string.c:117）与 DEL key IFEQ value（db.c:1469 delexCommand）把比较-交换原生内置，解锁可不再依赖 Lua。
03 标准实现：加锁 LOCK ACQUISITION

官方推荐的加锁姿势就一条命令。value 必须是客户端唯一标识（如 UUID + 线程/实例 ID），用于解锁时证明"锁是我的"。

# 加锁：仅当 key 不存在时写入，并设置 30s 过期 —— 全部原子完成
> SET lock:order:1001 c8f3a1 NX PX 30000
OK ← 加锁成功
(nil) ← key 已存在，加锁失败
SET 入口 t_string.c:435 setCommand 原子核心 t_string.c:87 setGenericCommand NX 判断 t_string.c:106-113 flags t_string.c:61-72 OBJ_SET_NX / OBJ_PX 命令文档 src/commands/set.json
  • 原子性来自单线程：setGenericCommand 里先 lookupKeyWriteWithLink 查键（t_string.c:104），再判断 NX/XX（t_string.c:106），最后写入 —— 整个流程在同一事件循环轮次内完成，没有其它客户端插进来的缝隙。
  • 选项解析：parseExtendedStringArgumentsOrReply（t_string.c:301）解析 NX/XX/EX/PX/GET/KEEPTTL/EXAT/PXAT 及 8.x 新增 IFEQ/IFNE/IFDEQ/IFDNE。
  • setnxCommand（t_string.c:446）是历史兼容入口：内部就是 setGenericCommand(OBJ_SET_NX)，但不再推荐单独使用（无过期时间）。
  • 为什么用随机 value：解锁时要"对值"再删，否则会误删别人的锁（见 04）；随机值让这把锁归属明确。
04 解锁：避免误删是核心难点 UNLOCK & THE MISTAKE

直接 DEL 是错误写法：锁过期后别人拿到了锁，你执行完再 DEL 就把别人的锁删了。正确做法是"先比对 value，再删除"，且两步必须原子 —— 用 Lua 脚本或 8.x 原生条件命令。

错误直接 DEL 非原子 · 会误删
  • A 加锁成功SET lock:o1001 uuidA NX PX 30000
  • A 业务执行超时，锁过期
  • B 加锁成功SET lock:o1001 uuidB NX PX 30000
  • A 执行完，直接删DEL lock:o1001← 删掉了 B 的锁！
  • C 趁虚而入，B 的临界区失守互斥被破坏
正确校验 value 再删 原子 · 安全
  • A 加锁成功SET lock:o1001 uuidA NX PX 30000
  • A 业务执行超时，锁过期
  • B 加锁成功SET lock:o1001 uuidB NX PX 30000
  • A 比对 value ≠ uuidA，不删Lua: if get==uuidA then del值不匹配，安全跳过
  • B 持锁正常执行完毕，B 自己解锁互斥保持
# 正确解锁 —— Lua 脚本（3.2+ EVAL），比较与删除原子完成
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:order:1001 c8f3a1
# 8.x 原生等价写法 —— DEL 带 IFEQ 条件，无需脚本
> DEL lock:order:1001 IFEQ c8f3a1
EVAL eval.c:633 evalCommand DEL db.c:1456 delCommand DELEX 条件删除 db.c:1469 delexCommand SET IFEQ t_string.c:117-151
  • Lua 脚本为何原子：Redis 的 Lua 执行器在脚本运行期间阻塞其他写命令（script.c / script_lua.c），脚本内的 GET + DEL 天然串行，等价于"内置事务"。
  • 8.x 的 DELEX：delexCommand（db.c:1469）实现 DEL key IFEQ value / IFNE value / IFDEQ digest / IFDNE digest（命令文档 src/commands/delex.json），比较在服务器内完成 —— 解锁不必再背一段 Lua。
  • 同样能用的还有 WATCH/DEL：WATCH + 读值 + MULTI 也能做 CAS（multi.c），但三趟往返、体验差，实践中不用它做锁。
一句话记忆：解锁必须"验明正身" —— value 是你写入的唯一标识，删除命令必须带上这个校验，且校验与删除必须原子。
05 可靠性四问：一把合格的分布式锁 FOUR PROPERTIES

评判锁是否合格，业界通用四个性质：互斥、防死锁、防误删、可容错。前三者由命令保证，第四者依赖部署与续期策略。

性质要解决的问题实现手段源码 / 配置
互斥同一时刻只有一个客户端持锁SET NX（不存在才写）t_string.c:106
防死锁持有者崩溃后锁能自动释放PX 过期时间t_string.c:63 OBJ_PX
防误删只能释放自己持有的锁value 唯一标识 + 原子校验删除（Lua / DEL IFEQ）eval.c:633 · db.c:1469
可容错单点故障不导致锁失效 / 锁丢失主从 + 哨兵 / 集群；极端场景 RedLockreplication.c · cluster.c
  • 过期时间怎么定：TTL 必须 > 业务最长执行时间，否则"锁先于业务失效"；但 TTL 太长又会让崩溃后的恢复变慢。通常取业务 P99 耗时的数倍。
  • 锁过期了还没执行完（续期/看门狗）：客户端定时（如每 TTL/3）执行 PEXPIRE key ttl 续期，业务结束或进程退出时停止 —— Redisson 的"看门狗"就是这个思路；底层就是 expire.c:726 expireGenericCommand（支持 NX/XX/GT/LT 条件）。
  • 可重入：同一线程重复加锁需计数。用 hash 存 {value: 次数}，Lua 里加锁时判断 value 相同则 HINCRBY —— 本质仍是"校验 + 原子操作"。
  • 公平性：SET NX 不保证先来先得；需要公平锁时用 zset 排队或独立队列，代价是性能。
06 RedLock：多数派算法与争议 REDLOCK & THE DEBATE

单节点锁在"主从切换"下会丢锁：主节点写入后未同步即宕机，从节点顶上后锁不存在，两个客户端同时持锁。RedLock 用 N 个独立 Redis 节点投票缓解，但它的正确性边界至今有争议。

1取当前时间t0 = now()
→
2依次对 N 节点加锁SET k uuid NX PX ttl，单节点超时极短
→
3统计成功数成功 ≥ N/2+1（如 5 节点需 ≥3）
→
4校验总耗时t1 - t0 < TTL，否则释放重试
→
5持锁执行业务时间 << TTL - 总耗时
  • 解决的问题：多数节点同时持有才叫持锁，单点宕机/网络分区不影响已形成的多数派。
  • Martin Kleppmann 的批评（《How to do distributed locking》）：GC pause 让持有者暂停超 TTL 后锁已过期、它醒来误以为仍持有 → 用 fencing token 才能根治；时钟跳跃 会让 TTL 判定失效；多数派算法在脑裂 + 时钟异常下无法保证严格互斥。
  • antirez 的回应（《Is Redlock safe?》）：分布式锁的正确性模型本就建立在"节点正常、时钟单调、网络分区可恢复"的假设上；RedLock 在现实的故障模型下已足够，极端语义（fencing）超出 Redis 定位。
  • 工程结论：Redis 锁适合"防并发重复操作"（幂等/串行化），不适合"强一致临界区"；后者请配合 fencing token 或换 ZooKeeper/etcd。Redis 官方文档把 RedLock 定位为"可用性优先、强互斥有限"的方案。
07 8.x 加持：条件命令原生 CAS 8.x NATIVE CAS

8.x 给 SET 与 DEL 都加上了条件比较选项，把"比较-交换"从 Lua 脚本下沉为服务器原语 —— 锁相关代码更短、更易审计。

# 条件加锁（SET ... IFEQ）：仅当旧值匹配时才写 —— 可用于"续期时确认仍持有"
> SET lock:o1001 c8f3a1 PX 30000 IFEQ c8f3a1
OK ← 值仍是我的，续期成功

# 条件解锁（DEL ... IFEQ）：值匹配才删除，否则返回 0 —— 替代 Lua
> DEL lock:o1001 IFEQ c8f3a1
(integer) 1 ← 删掉了自己的锁
SET IFEQ 实现 t_string.c:117-151 DELEX 实现 db.c:1469 delexCommand 文档 commands/set.json · commands/delex.json XDELEX t_stream.c:5079（stream 消息条件删除）
  • SET IFEQ/IFNE：按值比较（sdscmp），IFDEQ/IFDNE 按摘要比较（stringDigest，t_string.c:135-143），适合大 value 场景。
  • DELEX：DEL 的扩展形态，文档声明复杂度 O(1) for IFEQ/IFNE、O(N) 摘要比较。
  • 对锁生态的意义：Redisson 等客户端仍用 Lua 兼容老版本；但新项目可以只用 SET NX PX + DEL IFEQ 完成全部锁逻辑，无脚本依赖。
08 最佳实践清单 BEST PRACTICES

把上面所有结论落成可执行的检查项。

  • 加锁：只用 SET key uuid NX PX ttl；不要用 SETNX+EXPIRE 两步。
  • 解锁：value 比对 + 原子删除（Lua 或 8.x DEL IFEQ）；finally 中释放，防止异常路径遗留锁。
  • value：全局唯一（UUID + 实例/线程标识），确保"锁是我的"可验证。
  • TTL：取业务 P99 耗时的数倍；长任务配续期（看门狗），续期用 PEXPIRE 或条件 SET。
  • 容忍度：单机可接受丢失 → 主从 + 哨兵；要求多数派容错 → RedLock；要求严格互斥 + fencing → 换 etcd/ZooKeeper 或自增 token。
  • 监控：锁等待时长、持锁时长、续期次数、未释放锁残留（OBJECT ENCODING 看不出，用 SCAN + TTL 巡检）。
  • 别做的事：不要在锁里做重 IO/长事务；不要把锁 key 当业务 key 复用；不要依赖本地时钟做 TTL 计算（用服务器端相对时间）。
