Redis 事件循环：单线程如何扛住高并发

Redis 的高性能不靠多线程，而是一个线程把所有事做对：ae 事件库把"fd 可读可写"与"定时任务"统一成事件，交给 epoll 以 O(1) 复杂度等待就绪；一个循环内完成读命令、执行、写回复，全程无锁。8.x 又演进为 多 Reactor：IO 线程各自跑独立事件循环，命令执行仍回主线程。

01 为什么需要事件循环 WHY EVENT-DRIVEN

最朴素的服务器模型是"一连接一线程"：每个客户端占用一个阻塞线程，等待它发命令。连接数一多，线程数爆炸、上下文切换与锁竞争吞噬性能。Redis 换了一条路：单线程 + 非阻塞 IO + 多路复用。

阻塞式 accept/read
每连接一个线程，线程阻塞在 read 上等待数据。10 万连接 = 10 万线程，内存与调度开销不可承受。
一连接一线程模型（Java BIO 时代）
非阻塞 + 用户态轮询
fd 设 O_NONBLOCK，循环里逐个 read 试探。浪费 CPU 且代码丑陋。
O(N) 轮询
select / poll
内核帮你判断"哪些 fd 就绪"，但每次调用要拷贝整个 fd 集合，线性扫描，fd 数量受限。
O(N) 就绪检测 · 上限 1024（select）
epoll（Linux）
红黑树注册关注、就绪链表返回，只拷贝就绪的 fd，复杂度 O(就绪数)。
O(K) 返回 · 水平/边沿触发
事件循环（Redis 选择）
一个线程：先问 epoll "谁就绪了"，再按就绪列表逐个执行回调。没有锁、没有切换、没有线程栈开销。
aeMain → aeProcessEvents → aeApiPoll
  • 为什么 Redis 敢单线程：它的数据结构都在内存，单条命令微秒级完成；瓶颈从来不是 CPU，而是网络 IO 等待。多路复用让一个线程同时"等"几万个连接。
  • 单线程的三个红利：无锁（数据一致性靠顺序执行保证）、无上下文切换（时间片全花在命令上）、行为可预测（不存在并发 bug 与死锁）。
  • 代价：任何一条命令阻塞（如慢的 KEYS、大 key 删除）会卡住所有客户端 —— 所以才有 SCAN / UNLINK 这些渐进式命令，以及 8.x 的 IO 线程分担网络读写。
记忆锚点：事件循环 = "一个线程问内核：谁就绪了？然后挨个处理"。它把"等 IO"的时间让给别的连接，自己永远在干活或睡着，绝不空转轮询。
02 aeEventLoop：事件循环的心脏 CORE STRUCTS

整个事件机制由三张表构成：文件事件数组（fd 作下标，O(1) 注册）、就绪事件数组（一次 poll 的结果）、时间事件链表（周期/一次性定时器）。它们被 aeEventLoop（ae.h:79-93）统一持有。

/* ae.h:79-93 —— 事件循环本体 */
typedef struct aeEventLoop {
int maxfd; /* 当前注册的最大 fd */
int setsize; /* 数组容量（maxclients + 32）*/
aeFileEvent *events; /* 文件事件数组，events[fd] */
aeFiredEvent *fired; /* 就绪事件数组（本次 poll 结果）*/
aeTimeEvent *timeEventHead; /* 时间事件链表头 */
int stop; /* 置 1 退出主循环 */
void *apidata; /* 多路复用私有态（epoll → aeApiState）*/
aeBeforeSleepProc *beforesleep; /* 阻塞等待前回调 */
aeBeforeSleepProc *aftersleep; /* 唤醒后回调 */
} aeEventLoop;
掩码常量值含义
AE_NONE0未注册任何事件（该 fd 槽位空闲）
AE_READABLE1fd 可读时触发读回调（rfileProc）
AE_WRITABLE2fd 可写时触发写回调（wfileProc）
AE_BARRIER4写屏障：同一次循环中"先写后读"，用于写盘前先回包等顺序保证（ae.h:24-28）
结构 ae.h:79-93 aeEventLoop 文件事件 ae.h:52-57 aeFileEvent 时间事件 ae.h:60-70 aeTimeEvent 就绪事件 ae.h:73-76 aeFiredEvent
  • 数组 vs 链表的选择：文件事件用数组 —— fd 是天然下标，events[fd] 注册/查询 O(1)；时间事件数量少且无序，用双向链表，注册 O(1) 头插，删除打标记（ae.c:241 AE_DELETED_EVENT_ID）。
  • 一次 poll 的契约：aeApiPoll 把就绪 fd 写入 fired[]（fd + mask），主循环按数组顺序处理 —— 就绪多少处理多少。
  • 生命周期：aeCreateEventLoop(server.maxclients+CONFIG_FDSET_INCR)（server.c:3084）—— 数组容量 = maxclients + 32，随 aeResizeSetSize（ae.c:107）动态扩展。
03 多路复用抽象层 MULTIPLEXING ABSTRACTION

ae 不直接依赖 epoll：编译期按平台选择 ae_epoll.c / ae_kqueue.c / ae_evport.c / ae_select.c 之一，统一暴露 7 个函数。Redis 只认这套 API，换平台换实现。

Solarisae_evport.cEvent Ports：Solaris 原生事件机制

  • 统一 API 清单：Create（建 epoll/kqueue 实例）、AddEvent / DelEvent（增减关注）、Poll（等待就绪）、Resize（扩 events 数组）、Name（调试打印，epoll 返回 "epoll"）。
  • apidata 的作用：aeEventLoop.apidata 是个 void 指针，指向各平台私有状态（epoll 的 aeApiState）—— 抽象层的"插件槽位"。
  • 编译期而非运行时：无动态加载、无函数指针表开销，性能路径上就是直接调用。
04 epoll 实现细节 EPOLL ADAPTER

Linux 上 Redis 用 ae_epoll.c。私有状态只有两个字段：epfd（epoll 实例）与 events（epoll_event 就绪数组）。

} aeApiState;

tvp ? (tvp->tv_sec*1000 + (tvp->tv_usec+999)/1000) : -1);

等待 ae_epoll.c:89 aeApiPoll 注册 ae_epoll.c:54 aeApiAddEvent 创建 ae_epoll.c:19 aeApiCreate
  • 水平触发（LT）：Redis 不设 EPOLLET，保持默认水平触发 —— 没读完的数据下次 epoll_wait 继续报告，配合非阻塞 read 循环不会饿死其他连接。
  • epoll vs select：select 每次调用把 fd_set 从用户态拷进内核、线性扫描、FD_SETSIZE 1024 上限、触发后要重新注册；epoll 用红黑树维护关注、就绪链表只拷就绪项、O(1) 增删。这就是万级连接仍能扛住的底层原因。
  • 超时换算：timeval（秒+微秒）换算成毫秒给 epoll_wait：tv_sec*1000 + (tv_usec+999)/1000；无时间事件时传 -1 无限等待（ae_epoll.c:93-94）。
  • 信号中断：epoll_wait 返回 -1 且 errno==EINTR 时不 panic，继续循环 —— 事件循环必须对信号健壮（ae_epoll.c:110）。
05 事件主循环：一次迭代做了什么 MAIN LOOP

aeMain（ae.c:497）就是一个 while(!eventLoop->stop)：每圈调用 aeProcessEvents（ae.c:365）处理所有事件。一次迭代的完整顺序如下。

1beforeSleep 钩子写缓冲批量 flush · AOF 刷盘 · IO 线程协调
→
2计算 poll 超时最近时间事件决定阻塞多久（AE_DONT_WAIT 则 0）
→
3aeApiPoll 等待epoll_wait 阻塞，直到有 fd 就绪或超时
→
4afterSleep 钩子线程标记恢复 · 重新取 GIL
→
5分发文件事件逐个 fired[]：先读后写，AE_BARRIER 反转
→
6处理时间事件processTimeEvents 遍历链表（serverCron 等）
主循环 ae.c:497 aeMain 一次迭代 ae.c:365 aeProcessEvents 超时计算 ae.c:394 usUntilEarliestTimer 文件事件分发 ae.c:414-466 时间事件 ae.c:468-470 processTimeEvents
  • 读先于写（默认）：先执行读回调（可能产生回复），再执行写回调（把回复发出去）—— 一条命令在同一轮里"处理完就能回包"，减少延迟（ae.c:420-430 注释）。
  • AE_BARRIER 反转：持久化场景要求"先落盘再回包"（如每次写命令后 fsync），给写事件挂 BARRIER，同轮内先写后读（ae.c:431 / 455-463）。
  • 事件有效性复查：fe->mask & mask & AE_READABLE —— 处理读回调时可能删掉了同一个 fd 的事件（如客户端断开），分发前要确认事件还注册着（ae.c:433-438）。
  • 不空转：没有文件事件且没有时间事件时，epoll_wait 无限阻塞（tvp=NULL）；只有显式 AE_DONT_WAIT 才 0 超时立即返回（ae.c:390-403）—— CPU 永远不为"等"而烧。
06 一个客户端的完整生命周期 CLIENT LIFECYCLE

事件循环的意义在连接处理上最直观：一个连接从 accept 到回复，每一步都是一次事件回调。8.x 用 connection 抽象层统一 TCP / TLS / Unix socket，回调通过函数表注册。

  • 监听注册：listenToPort 里对每个监听 fd aeCreateFileEvent(el, fd, AE_READABLE, accept_handler, sfd)（server.c:2839）—— accept 也是普通文件事件。
  • 一次 accept 上限：server.max_new_conns_per_cycle 限制单轮 accept 数量（socket.c:303），防止惊群式循环把 CPU 打满、饿死已有连接。
  • 读写都是非阻塞：connSocketRead 对 EAGAIN 返回"没数据了"，写对 EAGAIN 表示"内核缓冲满，下次再试"（socket.c:135-176）—— 非阻塞 + 事件驱动是配套的。
  • 写事件是"按需"的：回复先进内存缓冲，能直接写完就不注册写事件（省一次 epoll 调用）；写不完才挂 AE_WRITABLE，可写时继续（clients_pending_write 机制，networking.c:2958）。
07 时间事件与 serverCron TIME EVENTS

除了文件事件，ae 还管理时间事件：到点执行一次（一次性）或周期执行。Redis 把核心后台任务都挂在 serverCron 这一个时间事件上，内部再细分频率。

  • 时间事件结构：aeTimeEvent 链表节点 —— id（单调递增）、when（单调时钟时间点）、timeProc、finalizerProc、refcount（防止递归中释放，ae.h:60-70）。

  • 影响主循环阻塞：最近一个时间事件的剩余时间就是 epoll_wait 的超时（ae.c:394 usUntilEarliestTimer）—— 时间事件和文件事件共享同一个"醒来"。
  • serverCron 职责：过期键清理、save / AOF 重写触发检查、客户端超时断开、集群 cron、模块 cron 等 —— 全部后台任务集中于此（server.c:1562-1857）。

08 beforeSleep / afterSleep 钩子 LOOP HOOKS

主循环每次阻塞等 epoll 之前调用 beforeSleep，醒来后调用 afterSleep（ae.c:382 / 411）。这两个钩子把"每轮都要做的杂事"集中起来，是 Redis 架构里最容易被忽略的调度点。

钩子执行时机典型职责

afterSleepaeProcessEvents:411 · poll 返回后IO 线程唤醒标记恢复（server.c:2162 afterSleep）· 模块 GIL 重新获取
注册 server.c:3216-3217 aeSetBeforeSleepProc / aeSetAfterSleepProc 主循环内调用 ae.c:382（前）/ ae.c:411（后） 主线程钩子 server.c:1947 beforeSleep · server.c:2162 afterSleep IO 线程钩子 iothread.c:847 IOThreadBeforeSleep · iothread.c:884 IOThreadAfterSleep
  • 写回复的批量优化：命令执行时只把回复追加进 client->reply 内存缓冲并标记 clients_pending_write；beforeSleep 里统一 handleClientsWithPendingWrites 一次系统调用写多个客户端 —— 避免每条回复一次 write 的小包开销（networking.c:2958）。
  • AOF 刷盘挂这里：flushAppendOnlyFile 在 beforeSleep 中调用 —— 上一轮的命令日志，在"睡觉前"统一落盘（与持久化笔记的写入链路对应）。
  • 两种 afterSleep 语义：主线程恢复处理 IO 线程送回的命令；IO 线程的 afterSleep 把 running 置 1，通知主线程"可以直接投递客户端、不用再发通知"（iothread.c:884-890）。
09 8.x IO 线程：多 Reactor 架构 THREADED IO

8.0 起 IO 线程不再是 6.x/7.x 的"主线程分配读写的从属线程"，而是每个 IO 线程拥有自己的 aeEventLoop（iothread.c:1006），自己跑 aeMain，负责一批客户端的读写与部分后台任务；命令的执行仍送回主线程 —— 数据一致性不破。

→

→
4送回主线程执行sendPendingClientsToMainThreadIfNeeded（iothread.c:881）
→
5主线程执行命令processCommand，写回复进缓冲

  • 每线程独立事件循环：t->el = aeCreateEventLoop(...)（iothread.c:1006），注册 notifier 读事件与 IOThreadCron 时间事件后 pthread_create（iothread.c:1041）—— 一个 IO 线程就是一个完整的小 Redis 事件循环。
  • 通信靠 event notifier：主线程把客户端列表 listJoin 进线程的 pending 列表后触发 notifier（管道写一字节），IO 线程被自己的事件循环唤醒（iothread.c:503-519）；反过来主线程也有 notifier 接 IO 线程的回传（iothread.c:1052 handleClientsFromIOThread）。
  • 缓存预取优化：prefetchIOThreadCommands 两阶段 —— 先批量发 prefetch 指令把 client 结构预取进缓存行，再访问数据，减少缓存缺失（iothread.c:524-552）。
  • 线程内后台任务：IOThreadCron 处理客户端 cron（超时、压缩等，iothread.c:893），把主线程从 O(客户端数) 的例行扫描里解放出来。
  • 上限与开关：io-threads 配置（默认关闭，≤ IO_THREADS_MAX_NUM 128，server.h:226）；开启后命令执行路径仍是单线程的，只是 IO 从主线程卸载。
记忆锚点：8.x 的 IO 线程 = "读得快、写得多"交给专用线程，执行还是主线程。它拆的是网络 IO 的墙，不拆数据一致性的墙 —— 所以不会引入普通多线程模型的锁地狱。
10 与 Netty 对比：Reactor 的两种实现 REDIS vs NETTY

Java 侧与 Redis 最像的是 Netty：都是事件驱动 + 多路复用。差别在于 —— Redis 为了"无锁的内存操作"坚持单线程执行；Netty 面向通用网络框架，用主从多线程换取更高吞吐。8.x 的 IO 线程让两者更接近了。

  • 为什么 Netty 必须多线程：Netty 承载的业务可能包含阻塞/耗时操作（数据库查询、文件 IO），单线程会饿死所有连接；Redis 命令全是内存操作，单线程不会成为 CPU 瓶颈 —— 这是模型选择的前提差异。
  • 结构同源：两者都来自 Doug Lea 的 Reactor 论文 —— 一个线程循环：select 等待 → 分发事件 → 处理回调。读懂 ae 再看 NioEventLoop 会非常顺。
  • 8.x 之后的收敛：IO 线程 + 主线程执行的架构，在思路上接近 Netty 的"IO 线程处理网络、业务线程处理逻辑"，但 Redis 仍坚持"业务永远单线程"。
