Redis 类型与编码全解

每一个键值对象都带着两个身份：逻辑类型 type（用户看到的 string / list / hash / set / zset…）与 物理编码 encoding（内存里实际怎么存）。同一类型可以随规模在多种编码间自动切换 —— 这是 Redis 在"省内存"与"高性能"之间找平衡的核心机制。

01 核心概念：robj 与 type / encoding 字段 THE redisObject

所有 value 的统一外壳是 struct redisObject（object.h:102），type 与 encoding 是其中的两个 4-bit 位字段。8.x 在此基础上演化出 kvobj：内嵌 key 与元数据，进一步省一次分配。

结构 object.h:102 struct redisObject 创建 object.c:107 createObject kvobj object.h:119 typedef · kvobjCreate 编码名 object.c:1302 strEncoding
  • type 决定"能做什么命令"：checkType（object.c:897）在命令执行前校验，类型不符报 WRONGTYPE。
  • encoding 决定"怎么存"：同一逻辑类型可对应多种编码，命令实现内部按 encoding 分支处理，对客户端完全透明。
  • 8.x kvobj 演进：把 key 内嵌进对象头（省一次 key 分配与寻址），并把过期时间等元数据以 8 字节块挂在对象前（object.h:44-64 内存布局注释），metabits 位图标记哪些元数据存在。
记忆锚点：type 是"合同"（对外承诺的语义），encoding 是"实现"（内存里选哪套结构）；客户端永远只感知 type，encoding 由 Redis 在写路径上自动升级。

编码常量集中在 object.h:75-91；OBJECT ENCODING 命令输出名由 object.c:1302 strEncoding() 统一映射。红色为 8.x 新增，灰线为已废弃（RDB 兼容仍保留编号）。

为什么编码是"实现细节"：客户端看不到 encoding，命令语义只由 type 决定；encoding 的存在让 Redis 对小数据用紧凑内存（listpack/intset），大数据用可扩展结构（dict/skiplist），切换对调用方完全透明。

  • 共享整数：0~9999（OBJ_SHARED_INTEGERS）直接复用全局共享对象（shared.integers[]），refcount 计数；LFU/LRU 淘汰场景走专用创建（createStringObjectFromLongLongForValue，object.c:394）。
  • embstr 的优势：对象头 + sds 头 + 数据在一次 malloc 里完成，内存局部性好、省一次分配与释放；缺陷：一旦 append 变长只能整体转为 raw。

  • int 编码的边界：只有整数值落在 LONG_MIN ~ LONG_MAX 才用 int（object.c:370），超出即退化为字符串。

  • Hash 的 8.x 升级链：LISTPACK → LISTPACK_EX（字段 TTL）→ TMPL_LP（共享字段模板）→ TMPL_ARRAY / HT。TMPL 系列把重复出现的 field 名内联成一份模板，值为数组或 listpack（object.h:89-90、aof.c:2427 isTmpl）。
  • intset 细节：内部始终有序，按最大元素自动升级 16→32→64 位；升 HT 是单向的（不做降级），删除元素不会回到 intset。
  • skiplist 是双结构：跳表提供 O(logN) 范围查询，同层 dict 提供 O(1) 按成员查分，两者共享节点（t_zset.c zset 结构）。
  • 升级不可逆：所有转换都是小→大单向，避免频繁抖动；阈值在 config 可调，但建议保持默认。
07 观察与调试：TYPE / OBJECT ENCODING INSPECTION

两条最常用的内省命令：TYPE key 看逻辑类型，OBJECT ENCODING key 看物理编码。实现都在 5 行以内，是理解编码体系的最佳上手点。

TYPE db.c:2187 typeCommand → db.c:1804 getObjectTypeName OBJECT object.c:1751 objectCommand 编码名 object.c:1302 strEncoding 类型名校验 object.c:897 checkType
命令输出与含义
SET k 123 → OBJECT ENCODING kint（数值直存）
SET k hello → OBJECT ENCODING kembstr（≤44 字节）
SET k <45+ 字节> → OBJECT ENCODING kraw（独立 sds）
SADD s 1 2 3 → OBJECT ENCODING sintset（全整数且小）；插入字符串后变 hashtable
ZADD z 1 a … 129 个 → OBJECT ENCODING z开始 listpack，超过 128 后变 skiplist
HSET h f v … 513 个 → OBJECT ENCODING h开始 listpack，超过 512 后变 hashtable
RPUSH l a b c → OBJECT ENCODING lquicklist（list 唯一编码）
XADD st * f v → OBJECT ENCODING ststream
WRONGTYPE 从哪来：命令执行前 checkType 比对对象 type 与命令要求；编码差异不会报错 —— 同一命令实现内按 encoding 分支，例如 hash 的 hget 同时支持 listpack 与 hashtable 两种取法（t_hash.c:1605 hashTypeGetFromListpack）。
08 8.x 演进：从 robj 到 kvobj 8.x EVOLUTION

8.10 的编码体系在 7.x 基础上做了三件事：listpack 全面取代 ziplist、对象模型升级为 kvobj、hash 家族新增三种紧凑编码并引入 array 类型。

kvobj 定义 object.h:119-127 kvobjCreate / kvobjSet / kvobjSetExpire 内存布局 object.h:24-64 头注释 TMPL 编码 object.h:89-90 Array 类型 server.h:898 OBJ_ARRAY · object.h:169 createArrayObject listpackex object.h:87 · t_hash.c 字段过期
  • ziplist → listpack：7.0 起 listpack 全面替换 ziplist；8.x 中 OBJ_ENCODING_ZIPLIST=5 仅保留编号用于 RDB 旧数据兼容，运行期不再产生。
  • kvobj 内嵌 key：键与值合并为一次分配（kvobjCreate），过期时间等元数据以 8 字节块前置于对象（metabits 位图标记存在性）——减少一次哈希表外的 key 分配和寻址。
  • hash 字段级 TTL：listpackex 在 listpack 上叠加字段过期元数据（listpackEx 结构，t_hash.c:1598-1635）；8.x 支持单个 field 设置过期。
  • 模板 hash（TMPL_LP / TMPL_ARRAY）：对字段名高度重复的 hash，把 field 名提成共享模板、只存值，值落在 listpack 或 sds 数组（defrag.c:783 有专门的分片整理实现）。
  • array 类型：OBJ_ARRAY（server.h:898）+ SLICED_ARRAY 编码（object.h:88），支撑 8.x 向量/定长序列场景（t_array.c、vector.c）。
