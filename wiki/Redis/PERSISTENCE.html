Redis 持久化：RDB 与 AOF 全解

内存是易失的。Redis 用两套机制把数据落盘：RDB 定时快照（紧凑、恢复快、有丢失窗口）与 AOF 追加日志（逐命令记录、fsync 精度可调、体积需要重写收敛）。8.x 起 AOF 演进为 Multi-Part：用 manifest 统一管理 base 快照与 incr 增量文件链。

01 为什么需要持久化 WHY PERSIST

Redis 默认把全部数据放在内存（server.db 的 dict/kvstore 中），进程退出即失。持久化的价值在于：崩溃后恢复与作为复制数据源（主从全量同步直接发 RDB）。

进程崩溃 / 断电 / 重启
内存数据全部丢失，靠磁盘上的持久化文件重建数据集。
server.c:7690 loadDataFromDisk
主从全量复制
从节点首次连主节点，主节点后台生成 RDB 快照直接推流（无盘复制时甚至不落盘），从节点加载后追赶 backlog。
replication.c · rdb.c:5292 rdbSaveToSlavesSockets
停机维护 / 数据迁移
SAVE / BGSAVE 产出快照文件，可离线归档或迁移到新实例。
server.c:1841（shutdown 保存）
  • 两条技术路线：快照（RDB，某时刻全量状态的二进制拷贝）vs 追加日志（AOF，把每条写命令记录下来，回放即恢复）。前者恢复快但丢失窗口大，后者丢失窗口可控但文件要重写。
  • 8.x 的融合：混合持久化（base=RDB 格式 + incr=AOF 命令）与 Multi-Part manifest，本质是把"快照 + 日志"组合成一套文件链，兼顾恢复速度与丢失窗口。
  • 不持久化的场景：纯缓存、可容忍全量重建的数据，可关闭 AOF 并配置 save "" 禁用 RDB，追求极致写性能。

  • 写入顺序（rdb.c:2027-2072）：magic → AUX → 模块前段 → 函数库 → hash 模板 → 逐库键值（rdbSaveDb 内含 SELECTDB / RESIZEDB / EXPIRETIME）→ 模块后段 → EOF → CRC64。

  • 8.x 模板化 hash：RDB_OPCODE_HASH_TEMPLATE 先把共享字段名注册为模板 id，之后同模板的 hash 只写"id + 值列表"，显著省空间（rdb.c:2046-2048）。
  • 校验：文件尾 8 字节 CRC64（rdb.c:2066-2070），加载时校验；rdb_checksum 关闭时跳过。
03 触发时机与 fork + COW TRIGGERS & COPY-ON-WRITE

RDB 生成几乎总是走子进程（BGSAVE）：fork 瞬间的内存页表快照 + 写时复制，让父进程在保存期间继续服务写请求而不阻塞。

1触发save 配置 / BGSAVE / shutdown / 全量复制
→
2fork 子进程子进程继承父进程页表（内存共享）
→
3子进程写临时文件rdbSaveInternal → rdbSaveRio
→
4父进程继续服务写操作触发 COW 复制脏页，子进程看到的仍是旧页
→
5rename 原子替换写成功才覆盖正式文件，失败保留旧文件
  • save 配置的周期性检查：serverCron 每秒检查 server.dirty >= sp->changes 且距上次保存超时（server.c:1714-1724）则 rdbSaveBackground。默认 900s 1 改 / 300s 10 改 / 60s 10000 改。
  • SAVE 命令是同步的：rdbSave（rdb.c:2180）在前台执行，期间阻塞所有客户端 —— 生产环境禁用，只用 BGSAVE / 配置触发。
  • 8.x 的 COW 优化：子进程保存完一个 db 的桶数组后，dismissKvstoreBucketsMemory 主动释放页缓存，减少后续写操作触发 COW 复制的代价（rdb.c:2056-2057）。
  • 写入原子性：rdbSaveInternal（rdb.c:2109）写 temp-<pid>.rdb，成功后 rename 覆盖目标文件 —— 崩溃只可能留下半成品临时文件，正式文件始终完整。
  • 无盘复制：repl-diskless-sync 时 RDB 通过 socket 直接推给从节点，不落盘（rdb.c:5292 rdbSaveToSlavesSockets）。
记忆锚点：RDB 的"快照一致性"来自 fork 的页表冻结 —— 子进程看到的是 fork 时刻的整棵内存树，与之后父进程的写入完全隔离，这就是它不需要加锁的原因。
04 AOF 写入链路 APPEND-ONLY CHAIN

AOF 的核心是"把每条改库命令变成可回放的日志行"。命令执行成功后，feedAppendOnlyFile 先把日志行追加进内存缓冲 server.aof_buf，再由事件循环统一刷盘。

1命令执行成功call() 内写路径完成
→
2feedAppendOnlyFile追加命令到 server.aof_buf（含 SELECT db）
→
3事件循环 beforeSleepflushAppendOnlyFile 统一刷盘
→
4aofWrite 写文件写入当前 incr 文件 fd（8.x）
→
5按策略 fsyncalways / everysec / no
入缓冲 aof.c:1661 feedAppendOnlyFile 刷盘 aof.c:1399 flushAppendOnlyFile 写文件 aof.c:1470 aofWrite 缓冲 server.h aof_buf / aof_flush_sleep
  • 协议复用：AOF 日志行就是 RESP 协议文本（*N\r\n$len\r\ncmd...\r\n），加载时走与客户端命令相同的解析与执行路径 —— 语义零损失。
  • SELECT 记录：feedAppendOnlyFile 在库号变化时写 SELECT n，保证回放时落在正确的 db。
  • 批量聚合：命令在 aof_buf 中累积，直到事件循环才一次性 aofWrite（aof.c:1470）；小于 4KB 的残留缓冲会被保留复用（aof.c:1568-1572），减少系统调用次数。
  • 部分写处理：nwritten < len 时保留未写部分（aof.c:1489/1550），下次继续；no-appendfsync-on-rewrite 可在重写期间跳过 fsync 减轻磁盘压力（aof.c:1576）。
05 appendfsync 三档策略 FSYNC POLICIES

write 只把数据交给内核页缓存，fsync 才真正落盘。三档策略（server.h:661-663）在"崩溃丢失窗口"与"写性能"之间取舍。

策略行为丢失窗口适用
alwaysAOF_FSYNC_ALWAYS 1最多 1 条命令金融级、绝不可丢；每条写命令后同步 fsync，吞吐最低
everysecAOF_FSYNC_EVERYSEC 2最多 1 秒默认；后台线程每秒 fsync，兼顾安全与吞吐
noAOF_FSYNC_NO 0取决于操作系统刷盘追求极限写性能；由内核决定何时落盘
  • everysec 的实现：flushAppendOnlyFile 检查 server.mstime - server.aof_last_fsync >= 1000 才 fsync（aof.c:1421 / 1600-1605），并记录 aof_last_fsync。
  • always 的实现：每次刷盘后立即 fsync（aof.c:1597），代价是每个事件循环都可能阻塞在磁盘 IO。
  • 崩溃语义：everysec 模式下进程崩溃但系统未崩，最多丢最近 1 秒日志；整机断电则未 fsync 的页缓存也可能丢。always 在任何崩溃下最多丢正在写的那一条。
06 AOF 重写：收敛文件体积 AOF REWRITE

追加式日志只增不减：一万次 INCR 会留下 1 万条日志，而当前值只有一个。重写 = 按当前内存状态重新生成一份最小 AOF（或 RDB 格式 base），把中间历史全部折叠掉。

1触发手动 bgrewriteaof / auto-aof-rewrite 阈值
→
2fork 子进程rewriteAppendOnlyFileBackground
→
3子进程重写快照按内存生成 base 文件（RDB 或纯命令）
→
4父进程收集增量重写期间的新命令进 aof_rewrite_buf
→
5合并落盘子进程快照 + 增量差量 → 新 base → 切换 manifest
触发 server.c:1741 auto-aof-rewrite 调度 server.c:1692-1696 aof_rewrite_scheduled fork aof.c:3197 rewriteAppendOnlyFileBackground 生成 aof.c:3117 rewriteAppendOnlyFile
  • 自动触发条件：auto-aof-rewrite-percentage 100 + auto-aof-rewrite-min-size 64mb —— 文件增长超过上次重写后 100% 且大于 64MB 才重写（server.c:1741）。
  • 与 BGSAVE 互斥：后台保存与重写不并行（server.c:1692），避免两个 fork 子进程争抢内存。
  • 重写期间的增量：父进程把新命令同时写入 aof_rewrite_buf（aofChildWriteDiffData），重写结束时合并进新文件 —— 保证新 base 覆盖到切换那一刻的状态。
  • 8.x 的产物：重写产出 .base.rdb（或 .base.aof）与新的 .incr.aof，旧文件转为 history 待清理（见 07）。
07 8.x Multi-Part AOF MULTI-PART MANIFEST

8.0 起 AOF 从"单个大文件"重构为 manifest + 文件链：一个 base 文件（快照，RDB 或 AOF 格式）+ 多个 incr 文件（增量命令，只有当前一个为 active）+ 历史文件（history，重写后待清理）。manifest 用文本声明式描述整条链。

# appendonly.aof.manifest —— 声明 base / incr / history（aof.c:64-71 示例）
file appendonly.aof.2.base.rdb seq 2 type b ← base 快照（重写产物，RDB 格式）
file appendonly.aof.1.incr.aof seq 1 type h ← history（旧增量，待清理）
file appendonly.aof.4.incr.aof seq 4 type i ← active 增量（当前写入）
类型命名说明
baseappendonly.aof.<seq>.base.rdb / .aof重写产出的全量快照；混合持久化下为 RDB 格式
incrappendonly.aof.<seq>.incr.aof增量命令日志；只有 seq 最大且 type=i 的一个是 active，写入只落它
historyappendonly.aof.<seq>.base/.incr.aof（type h）被重写淘汰的旧文件，加载时跳过、后台自动清理
结构 aof.c:155 aofManifestCreate（base + incr list + history list） 加载 manifest aof.c:242 aofLoadManifestFromDisk 启动打开 aof.c:734 aofOpenIfNeededOnServerStart 新增 incr aof.c:905 aofManifestAddNewIncr
  • 为什么改：旧单文件 AOF 重写要"写临时文件 + rename 覆盖"，崩溃时序复杂、大文件 I/O 重；Multi-Part 让 base 与增量物理分离，重写只是"换一个 base + 开一个新的 incr"，天然原子。
  • 命名规则（aof.c:74-80）：.base / .incr / .rdb / .aof / .manifest 后缀 + 单调递增 seq。
  • 生命周期：重写成功后旧 base/incr 全部降级为 history（aof.c:55-62 注释），后台 GC 自动删除；aofManifestFreeAndUpdate 维护内存 manifest 与磁盘文件一一对应。
  • 调试：INFO persistence 可看 aof_base_size / aof_current_size 等；目录下可见 appendonly.aof.manifest 与各分片文件。
08 混合持久化：aof-use-rdb-preamble HYBRID PERSISTENCE

7.0+ 默认开启：AOF 重写产出的 base 文件直接用 RDB 二进制格式（server.h:2347 aof_use_rdb_preamble），只有后续的 incr 增量才是命令日志。加载时先 rdbLoad 读 base（快），再回放 incr（准）。

1重写开始rewriteAppendOnlyFile 检查开关
→
2开启 → rdbSaveRioRDBFLAGS_AOF_PREAMBLE 直接写二进制
→
3关闭 → 纯命令rewriteAppendOnlyFileRio 逐 key 生成 RESP
→
4加载按文件头 magic 判断 RDB 段，再回放 incr
分支判断 aof.c:3140-3148 RDB 段 rdb.c:2027 rdbSaveRio(RDBFLAGS_AOF_PREAMBLE) 纯命令 aof.c:3013 rewriteAppendOnlyFileRio
  • 收益：base 是二进制快照 —— 文件更小、加载更快（无需重放海量命令）；incr 保留命令语义保证最新增量。这是 8.x Multi-Part 下 base 默认就是 .base.rdb 的原因。
  • 代价：base 段不可读（二进制），排查需要 redis-check-rdb / redis-check-aof 工具配合。
  • 配置：aof-use-rdb-preamble yes（默认）。关闭则退化为纯命令 AOF 重写。
09 启动数据加载 LOAD ON STARTUP

启动时 loadDataFromDisk（server.c:7690）按优先级决定从哪恢复：AOF 优先于 RDB（AOF 丢失窗口更小），8.x 还支持 preload-file 显式指定。

1preload-file 指定aof:/rdb: 前缀显式加载（8.x）
→
2AOF 开启？loadAppendOnlyFiles 按 manifest 加载 base + incr
→
3否则 RDBrdbLoad → rdbLoadRio → 逐键重建
→
4恢复完成继续加载复制 backlog / 开启服务
总入口 server.c:7690 loadDataFromDisk AOF 链加载 server.c:7745 loadAppendOnlyFiles RDB 加载 rdb.c:5124 rdbLoad → rdb.c:4677 rdbLoadRioWithLoadingCtxInternal
  • AOF 优先的原因：AOF 的数据通常比 RDB 新（丢失窗口更小）；两者都开启时以 AOF 为准，RDB 仅作兜底。
  • Multi-Part 加载：loadAppendOnlyFiles 按 manifest 顺序读 base（若是 RDB 格式走 rdbLoad）再回放全部 incr，history 文件跳过。
  • 损坏处理：AOF 尾部截断时日志告警并自动截断到最后一个完整命令（aofLoadTruncated），而非直接拒绝启动 —— 保证"能起来"优先；RDB 损坏则校验失败退出。
  • 8.x 升级路径：upgradeAofIfNeeded（server.c:7743）在升级场景把旧单文件 AOF 转换为新 manifest 结构，避免启动即触发前台重写。
10 对比与选型 RDB vs AOF vs HYBRID

三者不是互斥关系：默认配置下它们同时工作（RDB 兜底 + AOF 精细恢复），8.x 的混合 base 又让 AOF 重写后的恢复速度接近纯 RDB。

维度RDBAOF（纯命令）AOF（混合 base）结论
文件格式二进制快照RESP 命令文本RDB base + 命令 incr混合兼具
恢复速度快（直接载入）慢（重放命令）快（base 直载 + 少量 incr）RDB ≈ 混合 > 纯 AOF
丢失窗口取决于 save 间隔（最大可能很大）everysec ≤1s / always ≤1 命令同 AOF（incr 控制）AOF 系明显更小
体积紧凑大，需重写收敛base 紧凑，整体优于纯 AOFRDB ≤ 混合 < 纯 AOF
可读性不可读可读可审计base 不可读，incr 可读纯 AOF 最适合审计
对写性能几乎无感（fork 开销）everysec 下开销小同 AOF三者差异可控
适用可接受较大丢失、要快速重启、纯缓存敏感数据、严格不丢默认推荐：两者都要混合 > 纯 AOF > RDB
  • 默认行为：appendonly yes 时启动加载以 AOF 为准；RDB 仍可保留作为兜底与复制源。
  • 生产建议：always 只用于"单条都不能丢"的强约束场景（吞吐损失明显）；常规业务 everysec 足够；纯缓存可关掉 AOF。
  • 监控项：INFO persistence 看 rdb_last_bgsave_status、aof_last_write_status、aof_rewrite_in_progress；重写/保存失败必须告警（文件可能停更）。
